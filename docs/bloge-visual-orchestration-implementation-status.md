# BLOGE 可视化编排实现状态审计

状态：Current Implementation Snapshot

代码基线：`resource-gateway-examples`

本文不是新的愿景文档，而是把当前代码事实、已完成闭环、仍缺口和下一步工程重点对齐起来。它用于防止设计文档、README 和实际实现发生语义漂移。

## 1. 当前结论

Phase 1 的核心闭环已经从“设计草案”进入“可运行示例项目”：

```text
Operator Library / Resource Design Contract
        -> Visual Operator Catalog
        -> GraphDraft
        -> Schema-aware Connection / Validation
        -> BLOGE DSL Generation
        -> Compile / Run
        -> Immutable Publication
```

现在最重要的判断不是“有没有画布雏形”，而是：这个示例已经具备通用画布的控制面骨架，但仍不是完整低代码平台。它可以严肃演示用户算子库、Java OperatorRegistry 投影、资源虚拟算子、OpenAPI 辅助生成 resource design contract、AsyncAPI preview 生成 event/message/webhook operator-library 草案、remote-worker / AI-tool / event-source / message-handler / webhook binding 合同、schema 约束连线、草稿、发布和运行；并且已经能在 catalog/validator 层识别当前 request-response runtime 不能执行的 streaming/durable/remote-worker/AI-tool/event/message/webhook operator，其中 streaming/durable 草稿在 schema 有效时进入 runtime-blocked 设计态，允许 warning-acknowledged `DESIGN` publication，但仍阻断 compile/run/默认 executable promotion；还没有覆盖 durable 实例、真正的 worker/subgraph marketplace、AI tool invocation runtime、事件/消息/webhook ingress runtime、生产 IAM 后台和多人协作。

### 2.1 本轮增量状态

- Post-apply executable readiness evidence refresh 现在补上稳定 id 精确 replay：外部 runtime workflow 在提交同一 `refreshedBindingId` / `refreshedActivationId` / `refreshedIntegrationId` 后，即使原响应丢失、重试时仍携带旧 `expectedPreviousOperatorFingerprint` 与当前 `expectedCurrentOperatorFingerprint`，服务端也会识别当前 active binding/activation/integration chain 已由这次 refresh 形成，并返回已有 refreshed lineage，而不是把当前 active binding 的新 fingerprint 误判成 stale。该 replay 只在三类 refreshed id 全部命中当前完整 active chain、当前 binding 指向上一条 superseded binding、fingerprint 期望值与 lineage 对齐时触发；真实 id 冲突或错误 fingerprint 仍按原 gate 拒绝，避免跨系统重试把不相关证据链吞掉。
- `bloge.visualRuntimeEvidenceWindow.v1` 现在把 imported/user operator library owner 作为 runtime evidence 的一等过滤维度：implementation binding、adapter activation、rollout observation 和 executable lowering integration 会按当前 catalog `operatorLibraryId` 归属投影到 evidence item；当当前 catalog 不再能给出 owner 时，会从持久化 implementation binding 的 handoff operator contract snapshot 恢复 owner，并通过 bindingId 传递给 activation、rollout observation 和 lowering integration，避免用户算子库删除、替换或 scope 隐藏后历史 runtime fact 失去归属。窗口返回 `operatorLibraryIdCounts`，并支持 `operatorLibraryId` 与 `evidenceKind`、`operatorRef`、binding、activation、lifecycle、rollout signal、`breachedOnly` 组合过滤。浏览器 Workspace Overview 的 Runtime Evidence 面板同步增加算子库过滤控件和上下文文案，让 runtime-plane 团队可以按用户算子库边界领取/审计 schema-only、design-only、external-runtime-bound 和 rollout-risk 证据，而不是只能按单个 operatorRef 反复切分。
- Shared JSON Schema compatibility 现在把 `allOf` 作为保守交集约束进入服务端 schema-to-schema gate 和 value matching：target `allOf` 的 base 与每个 branch 都必须能被 source 证明满足；source `allOf` 只有在 base 或某个显式 typed / finite-domain constituent 已足以证明兼容时放行，否则返回 `source allOf has no constituent...` 诊断并阻断，避免 typeless composition 被误当成可安全连线。该规则会被 GraphDraftValidator、connection preflight、operator-library replacement drift 和 runtime implementation contract-diff gate 共同消费；Browser Composer 本地 `schemaType`、literal value matching 和 advisory `schemaCompatibilityIssue` 也已镜像该规则，让 source picker/hover blocked reason 在服务端最终裁决前先给出一致提示。更复杂的跨 branch JSON Schema 求解仍保持保守拒绝，而不是在画布里伪造不可证明的兼容性。
- Shared JSON Schema compatibility 现在会阻断 source object 动态字段与 target optional property 的 schema 碰撞：当 source `additionalProperties`、`unevaluatedProperties` 或匹配的 `patternProperties` 可能产生 target 已声明但非 required 的字段时，该动态字段 schema 也必须能 feed target property schema；source `propertyNames` 能证明该 key 不可能出现时不会误报。该规则同时进入 GraphDraftValidator 的 binding/edge 校验和 runtime implementation contract-diff gate，避免用户导入算子库的动态 map payload 在画布连线或 schema drift 审阅时绕过可选字段约束。
- Shared JSON Schema gate 现在支持 schema-form `not` 排除域：`const`、标准/custom enum、`pattern`、`format`、类型以及已支持的 object/array/string/numeric 约束都会进入结构校验、默认值校验、运行时 context 校验、静态 literal/schema compatibility 和浏览器本地提示；schema-to-schema compatibility 现在还能用 source numeric 区间、string length、array item count、array item/prefixItems/受限 `items` / `unevaluatedItems` residual policy vs `not.contains`、object property count、object required/property schema impossibility 和 required property name vs excluded `propertyNames` 证明它与 target `not` 排除域 disjoint，能证明时不再误阻断，无法证明时继续保守阻断。`if`/`then`/`else` 已进入同一受限 visual schema subset：条件关键字必须是 schema object，default/runtime/static literal value matching 会按 `if` 命中结果应用 `then` 或 `else`，schema-to-schema compatibility 只有在 source 可证明命中或避开 `if` 时按单分支放行，无法证明时继续要求所有可能分支兼容。object `minProperties` compatibility 现在会把 source `required` 字段集合作为保守属性数下界证明，避免常见业务对象 schema 因未显式声明 `minProperties` 而被误阻断。array `contains` compatibility 现在不再只依赖显式 source `contains`：source `items` / `prefixItems` 搭配 `minItems` / `maxItems` 能证明 target `minContains` / `maxContains` 的匹配元素上下界时也会放行；array `items` 现在支持 schema object 或 boolean residual policy：`items=false` 禁止 `prefixItems` 后的剩余项，`items=true` 表示剩余项无约束；受限 array `unevaluatedItems` 也进入同一 gate：只支持 boolean 或 schema object；当 `items` 不存在时，`unevaluatedItems=false` 禁止 `prefixItems` 后的剩余项，schema object 则约束剩余项，default/runtime/static literal 和 schema-to-schema compatibility 都复用该 residual item policy。
- Shared JSON Schema object dependency compatibility 现在能识别 source `dependentRequired` 对 target `dependentSchemas` 的条件证明：当 target dependent subschema 在 trigger 出现时要求某个伴随字段，source 只要通过同一 trigger 的 `dependentRequired` 和字段 schema 证明该字段必然存在且类型兼容，就不再误判为无法保证 dependent schema；反向地，source `dependentSchemas` 在 trigger dependent subschema 中显式 `required` companion 字段时，也能证明 target `dependentRequired`，两种常见 schema 表达不再因为写法不同而被误拒；伴随字段类型不满足 target subschema 时仍按 `visual.binding.typeMismatch` / contract-diff 路径保守拒绝。
- Shared schema compatibility 现在把 target `const` 作为显式 finite value domain 诊断：`const` 与标准/custom enum 仍共享同一套可证明有限域推理，但服务端 GraphDraftValidator、runtime implementation contract-diff gate 和浏览器本地 hint 会把 `target const [x]` 与 `target enum [...]` 区分开，避免用户导入算子库排错时把固定值约束误读成普通枚举约束。
- Shared finite value domain equality 现在按 JSON schema 值语义统一：服务端 schema compatibility、结构/default/runtime validator 和浏览器本地 hint 都会把 `1` 与 `1.0` 视为同一数值，并递归比较数组与对象值；schema 结构校验中的 `const` vs `enum` / custom enum `values` 交叉检查也复用同一语义，避免外部算子库导入时因 Java 数字包装类型或浏览器对象字段顺序造成 enum/`const`/finite `not` 的假不兼容或假通过。
- Shared numeric schema compatibility 现在区分 `number`/`decimal` 与 `integer` 的可赋值关系：`integer` source 仍可 feed `number` target，但 `number` 或 `decimal` source 只有在通过 integral `multipleOf`（例如 `1`、`2`）证明不会产生小数时，才能 feed target `integer`；该规则同时进入 GraphDraftValidator、connection preflight 和浏览器本地 hint，避免金额、计数、期限等复杂业务字段被小数域误接到整数输入。
- Browser Composer 的本地 `schemaCompatibilityIssue` 现在也镜像上述 optional/dynamic object collision 规则：source picker、拖拽 hover 和本地 blocked reason 会提前暴露 `additionalProperties` / `patternProperties` 产生的 optional key schema mismatch，并尊重 `propertyNames` 排除证明；服务端 connection preflight 仍是最终裁决。该路径已补充 `/api/visual/connections/check` 和真实浏览器 source picker 回归，覆盖 schema-only 用户算子 root-object output 连接到 optional-field target 时的 blocked option、服务端拒绝状态和无 edge/binding 副作用。

## 7. 反熵控制

为了让这个示例继续朝通用画布演进，而不是退化成一次性 demo，后续改动必须守住这些规则：

1. 新的可拖拽能力必须先进入 `OperatorDefinition`，不能只在前端 `app.js` 里硬编码。
2. 新的连接或绑定语义必须进入 `GraphDraftValidator`、`/api/visual/connections/check` 和必要的 `/api/visual/connections/candidates` 读模型，不能只靠浏览器判断。
3. 新的 executable draft 必须保留 operator fingerprint snapshot 和 node-level operator definition snapshot，并在 compile/run/publish 前验证。
4. 新的 resource authoring 信息必须通过 `ResourceDesignContract` 或等价合同进入 catalog projection，不能污染 runtime `ResourceDescriptor` 的调用职责。
5. 新的发布/运行能力必须返回结构化 `VisualDiagnostic`，不能只返回字符串错误。
6. README 可以描述用户体验，但协议字段和不变量必须以 `docs/bloge-visual-orchestration-implementation-status.md` 和代码为准同步更新。
