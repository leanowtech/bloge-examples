# 用业务语言把取消费政策变成可信业务能力

这是一份面向业务人员的 v1.4.5 现场演示导演脚本。主角是客服政策负责人小李。她不写代码，也不需要理解 MCP、DSL、YAML、Schema、binding、接口地址或内部标识。她只负责业务目标、判断依据、政策规则和标准答案。

Codex 负责把小李的表达翻译为平台中的事实、场景、处置和解法；平台负责校验、留证和守门；工程师只履行平台生成的交接单；人工负责人保留标准答案批准和上线签署权。

环境安装、Codex 配置、工程履约命令和故障排查见 [在 Codex 中使用 Resource Gateway Agent TDD MCP](resource-gateway-agent-tdd-mcp.md)。

## 1. 这场演示证明什么

演示回答一个问题：

> 一个不写代码的客服政策负责人，能否只用业务语言，把“网约车取消费该怎么处理”变成可验证、可发布、可运营的客服能力？

观众最终应看到五件事：

1. 小李只讲业务，Codex 自己建立所需的业务契约。
2. 缺少事实来源或写入实现时，系统生成明确的工程交接，不把技术问题甩给小李。
3. 小李在五面板看板里核对规则、处置、事实、标准案例和发布门，不看代码。
4. 逻辑验证不访问真实依赖；真实写入只在沙箱中由平台依据已批准案例受控执行并回读对账。
5. 发布后可以复用，并用不含业务载荷的命中、升级和处置分布驱动下一轮政策修订。

## 2. 角色与现场画面

| 角色 | 现场动作 | 明确不能做 |
| --- | --- | --- |
| 小李，客服政策负责人 | 与 Codex 对话；核对标准答案和看板；作业务决定 | 提供技术定义；写规则代码 |
| Codex，业务工具搭建助手 | 发现积木；建立四类业务资产；验证；提交交接与发布 | 批准自己的标准答案；替工程师绑定实现 |
| 特征工程师 | 让“责任方”和“免费时段”两个事实可被稳定判断 | 改政策规则 |
| 通用工程师 | 实现退款和转人工工单，并提供回读对账 | 经 Codex/MCP 修改业务合同 |
| 业务签署人 | 在看板核对五面板并签署上线 | 代替 Codex 创作 |
| 平台 | 隔离权限、校验、零外呼测试、受控写、对账、冻结发布 | 猜测缺失事实 |

推荐投屏：左侧为小李与 Codex 的对话，右侧为 `http://localhost:8081/agent-tdd.html`。终端、网络请求和技术结构默认不投屏。

## 3. 会前准备与开演门

保障人员在独立终端完成操作手册第 2、3 节：

1. 启动 Resource Gateway，并显式开启取消费 demo adapter。
2. 给 Codex 的进程只注入 Agent token。
3. reviewer、feature-engineer、instruction-engineer 三份 token 由人分别保管，Codex 进程不可继承。
4. 在 Codex 输入 `/mcp`，确认 `rg_read`、`rg_author`、`rg_execute`、`rg_govern` 全部已连接。
5. 打开业务看板，但不要提前批准或签署。

必须检查以下入口可见：

- 可用业务积木概览；
- 事实定义与特征工程交接；
- 场景、处置、解法创作；
- 标准案例提议、GREEN、readiness 与发布。

如果 Codex 说“没有规则编写入口”，先检查 `.codex/config.toml` 的 `enabled_tools` 是否包含 `rg.library.overview.get`、`rg.feature.handoff`、`rg.scenario.define`、`rg.instruction.define` 和 `rg.solution.compose`，然后彻底重启 Codex。不要让小李补写 DSL。

## 4. 开场约定

小李在新的 Codex 任务中输入：

```text
你是我的业务工具搭建助手。

我只负责说明业务目标、判断依据、规则和标准答案。请你使用已经连接的业务工具平台，自行完成能力发现、契约设计、实现草稿、检查和修正。

和我沟通时只使用业务语言，不展示代码、配置、数据结构、内部标识或技术诊断。缺少业务含义时可以问我一个明确问题；缺少系统实现时请建立工程交接，不要让我提供技术方案。每完成一幕就停下来让我核对。不要替我批准标准答案，不要替我签署上线，也不要发布未经签署的内容。

请用一句话复述我们的分工，然后等我提出业务目标。
```

正确回应应说明：小李负责业务真相和上线决定，Codex 负责技术翻译与平台操作。

## 5. 第一幕：说清目标与业务世界

### 小李输入

```text
我是网约车业务的客服政策负责人。

我想把“取消费纠纷怎么处理”做成客服助手可以直接使用的业务能力。客服选择一个争议订单后，需要得到三种处置之一：全额免除取消费、维持原收费、转人工复核。

做判断至少需要知道两件事：这次取消主要由谁负责，以及订单是否仍在免费取消时段内。责任方可能是无人担责、司机、乘客或平台。订单由客服在当前会话中选择。

请先检查平台已经有哪些可复用的业务积木。缺少的事实能力请先建立清晰的业务约定并交给对应工程师，不要猜系统实现，也不要让我填写接口或数据结构。完成后只告诉我：你理解的判断依据、可能处置、哪些事实已经可用、哪些正在等待工程接入。
```

### Codex 后台应完成

- 先读取当前作用域的业务积木概览。
- 建立“责任方”“是否在免费取消时段”“当前选择的争议订单”三项事实契约。
- 将前两项确定性事实保持为设计态，并分别建立特征工程交接单。
- 将“订单选择”识别为人工交互事实，不伪造自动求值实现。
- 不创建第二套同义事实，不向小李展示内部引用。

### 本幕成功信号

- 小李看到三项业务事实和三种处置的白话摘要。
- “责任方”“免费时段”显示等待特征工程；订单选择显示为用户提供。
- Codex 没有询问接口地址、字段类型、DSL 或 YAML。
- 若业务含义不完整，Codex只问业务问题；若平台工具缺失，明确报平台维护待办并停止。

## 6. 第二幕：工程履行事实，再由小李确认规则

幕间由保障人员按操作手册第 3.1 节履行两个特征交接。看板应把两项事实从“设计态”更新为“已验证/就绪”。Agent token 调同一履约地址必须得到 403。

### 小李输入

```text
事实来源已经由工程师接好了。请按以下政策设计处理规则：

1. 无人担责，并且还在免费取消时段内：全额免除取消费。
2. 司机责任：维持原收费。
3. 乘客责任：维持原收费。
4. 平台责任：转人工复核。
5. 其他没有明确覆盖的情况：转人工复核，不能自动猜。

全额免除需要写入退款系统；转人工复核需要创建客服工单；维持原收费不改业务系统。每种处置都必须说明原因。

请自行形成可执行草稿并完成平台检查。先不要运行案例，也不要发布。完成后只用业务表格向我说明：每条规则会得到什么处置、哪些处置还等待工程实现。
```

### Codex 后台应完成

- 建立三项处置契约，并填写明确的业务名称；结果都包含处置结果与原因。
- “全额免除”和“转人工复核”保持设计态，声明下游与对账要求；“维持原收费”只复用平台已批准的只读实现。
- 建立含四条规则和兜底分支的场景，再组合为同一取消费解法。
- 对草稿执行服务端预检；技术错误由 Codex 根据安全诊断自行修正。
- 为两个设计态写处置建立一张写工程交接单，然后停止。

### 小李在看板核对

| 责任方 | 免费时段 | 业务处置 |
| --- | --- | --- |
| 无人担责 | 是 | 全额免除取消费 |
| 司机 | 任意 | 维持原收费 |
| 乘客 | 任意 | 维持原收费 |
| 平台 | 任意 | 转人工复核 |
| 其他 | 其他 | 转人工复核 |

本幕不能因为写实现尚未完成而让 Codex自行填一个“看起来像”的实现引用。正确状态是“业务规则已形成，两个写处置等待工程履约”。

## 7. 第三幕：工程实现处置，业务给出标准答案

幕间由通用工程师按操作手册第 3.1 节履行退款与工单两项交接。交接单全部完成后应为 `IMPLEMENTED`，但尚未 `CLOSED`；只有真实写对账成功才能关闭。

### 小李输入

```text
写处置已经由工程师实现。以下四个案例是业务标准答案，不能为了迁就当前实现而修改：

1. 免费时段内且无人担责，应全额免除取消费。
2. 司机责任，应维持原收费。
3. 乘客责任，应维持原收费。
4. 平台责任，应转人工复核。

请把它们整理为待我确认的标准案例，并检查是否覆盖每条明确规则。不要替我批准，也不要开始真实写入。
```

### Codex 应完成

- 提议四条 GOLDEN 标准案例，分别保留小李给出的业务意图。
- 标准答案保持独立，不根据实现结果改写。
- 告诉小李需要到看板逐条确认，并停止在人工停点。

### 人工停点一：批准业务应然

小李在看板逐条打开详情，核对“前提事实、期望处置、业务意图、负责人”，再批准。审批期间如案例被修改，服务端拒绝旧 revision，必须刷新重审。

成功信号：四条案例均为 ACTIVE；Codex 不能用 Agent token 调批准接口；看板能显示规则矩阵、处置清单、事实卡和四条案例。

## 8. 第四幕：GREEN、受控写对账与上线签署

### 小李输入

```text
我已经在看板确认了四条标准案例。请继续做上线前验证。

先验证业务规则对四个标准案例都成立。逻辑验证不能访问真实业务系统。逻辑通过后，由平台按批准案例在本地沙箱验证退款和工单写入，并回读确认结果一致。

请把“逻辑是否正确”“写入是否已对账”“还缺哪个人工决定”分开告诉我。如果只缺上线签署，就停下来等我看板操作。不要替我签署或发布。
```

### 平台应完成

- GREEN 逻辑验证中 `realExternalCalls=0`，四条案例均为 GREEN_PASS。
- 只有 `GREEN + GO + handoff=IMPLEMENTED` 时，平台才派生内部写权限。
- 平台只消费当前 ACTIVE GOLDEN，在本地 demo ledger 中执行退款和建单并回读。
- 对账为 RECONCILED 后，写交接单从 IMPLEMENTED 变为 CLOSED。
- 重复相同 GREEN 不重放 CLOSED 交接；过程丢失时返回 RECOVERY_REQUIRED，不自动猜测重试。

### 人工停点二：五面板审阅与签署

小李打开解法的业务审阅窗口，依次核对：

1. 规则矩阵；
2. 三项处置及写入影响；
3. 三项判断依据及来源状态；
4. 四条红绿案例；
5. 发布卡中的逻辑、实现、写对账和签署门。

全部一致后输入新的签署编号。任何一项漂移都必须重新验证与签署。

## 9. 第五幕：发布、复用与运营回流

### 小李输入

```text
我已经在看板完成上线签署。请确认规则、标准案例、工程实现和对账证据从签署后都没有变化；全部一致时再发布。

发布后，请用“免费时段内且无人担责”的业务情形演示一次客服调用，并告诉我命中了哪条规则、得到什么处置。最后只汇报累计调用、规则命中、转人工比例和处置分布，不展示订单内容、认证信息或内部指纹。
```

### 成功信号

- 发布物类型为 Solution，旧签署不能授权变化后的实现。
- 调用前平台分别求值确定性事实并签名；篡改事实值时调用被拒绝。
- 正常调用得到“全额免除取消费”及业务原因。
- 相同幂等键重放同一结果，运营累计只增加一次。
- 运营看板能显示命中、升级、处置分布和政策缺口，但不保存订单、事实值、结果正文、原因或 token。

## 10. 主持人故障分流

| 现场表现 | 应停在哪一幕 | 处理人 | 不应做什么 |
| --- | --- | --- | --- |
| Codex 看不到规则/交接工具 | 会前 | 平台维护 | 让业务人员写 DSL |
| 事实仍是设计态 | 第一幕 | 特征工程 | 用假数据冒充已接入 |
| 写交接未 IMPLEMENTED | 第二幕 | 通用工程 | Agent 自填 binding |
| 标准案例未 ACTIVE | 第三幕 | 业务 reviewer | 跳过批准直接 GREEN |
| GREEN 通过但写未对账 | 第四幕 | 平台/下游负责人 | 把逻辑绿说成真实写成功 |
| readiness 不可发布 | 第四幕 | 按 remaining limitation 分流 | 反复盲重试 |
| 签署后资产变化 | 第五幕 | 重新验证与签署 | 复用旧签署 |

## 11. 会后停止与验收证据

停止 Resource Gateway：

```bash
./scripts/stop-examples.sh resource-gateway
```

仓库内的可重复验收用例是 `CancelDisputeSolutionOperationalJourneyTest`。它真实经过 HTTP MCP initialize、initialized、tools/list、tools/call，验证 Agent 不能履行两类工程交接，使用四条 GOLDEN，要求真实 Chrome 打开五面板且 `skipped=0`，并贯穿 GREEN 零外呼、平台受控写对账、发布、运行复用、运营聚合和特征 token 篡改拒绝。

这份自动验收证明平台路径可运行；现场仍要证明业务人员只用上述自然语言提示即可让当前 Codex 完成同一业务旅程。两者不能互相冒充。
