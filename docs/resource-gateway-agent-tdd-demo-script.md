# 用业务语言把取消费政策变成可信业务能力

这是一份面向业务人员的 v1.4.6 现场演示导演脚本。主角是客服政策负责人小李。她不写代码，也不需要理解 MCP、DSL、YAML、Schema、binding、接口地址或内部标识。她只负责业务目标、判断依据、政策规则和标准答案。

Codex 负责把小李的表达翻译为平台中的事实、场景、处置和解法；平台负责校验、留证和守门；工程师只履行平台生成的交接单；人工负责人保留标准答案批准和上线签署权。

环境安装、Codex 配置、工程履约命令和故障排查见 [在 Codex 中使用 Resource Gateway Agent TDD MCP](resource-gateway-agent-tdd-mcp.md)。

## 1. 这场演示证明什么

演示回答一个问题：

> 一个不写代码的客服政策负责人，能否只用业务语言，把“网约车取消费该怎么处理”变成可验证、可发布、可运营的客服能力？

观众最终应看到五件事：

1. 小李只讲业务，Codex 先盘点业务能力库，再通过多轮业务对话定义判断事实，并精确复用或建立所需契约。
2. 缺少事实来源或写入实现时，系统生成明确的工程交接，不把技术问题甩给小李。
3. 小李在五面板看板里核对规则、处置、事实、标准案例和发布门，不看代码。
4. 逻辑验证不访问真实依赖；真实写入只在沙箱中由平台依据已批准案例受控执行并回读对账。
5. 发布后可以复用，并用不含业务载荷的命中、升级和处置分布驱动下一轮政策修订。

## 2. 角色与现场画面

| 角色 | 现场动作 | 明确不能做 |
| --- | --- | --- |
| 小李，客服政策负责人 | 说明事实含义、取值口径、异常边界和规则；核对标准答案和看板；作业务决定 | 提供技术定义；写规则代码 |
| Codex，业务工具搭建助手 | 盘点业务能力库；逐项澄清业务事实；精确复用已有能力；建立缺失契约；验证；提交交接与发布 | 批准自己的标准答案；替工程师绑定实现 |
| 特征工程师 | 让“责任方”和“免费时段”两个事实可被稳定判断 | 改政策规则 |
| 通用工程师 | 实现退款和转人工工单，并提供回读对账 | 经 Codex/MCP 修改业务合同 |
| 业务签署人 | 在看板核对五面板并签署上线 | 代替 Codex 创作 |
| 平台 | 隔离权限、校验、零外呼测试、受控写、对账、冻结发布 | 猜测缺失事实 |

推荐投屏：左侧为小李与 Codex 的对话，右侧为 `http://localhost:8081/agent-tdd.html`。终端、网络请求和技术结构默认不投屏。

## 3. 会前准备与开演门

保障人员在独立终端完成操作手册第 2、3 节：

1. 启动 Resource Gateway，并显式开启取消费 demo adapter。
2. 给 Codex 的进程只注入 Agent token。
3. reviewer、feature-engineer、instruction-engineer 三份 token 由人分别保管，Codex 进程不可继承。
4. 在 Codex 输入 `/mcp`，确认 `rg_read`、`rg_author`、`rg_execute`、`rg_govern` 全部已连接，且四个连接都固定 `X-RG-Surface=BUSINESS_SOLUTION`。
5. 打开业务看板，但不要提前批准或签署。

必须检查以下入口可见：

- 业务能力库概览，且能区分“已可复用”“用户提供”“等待工程接入”“待业务定义”；
- 事实定义与特征工程交接；
- 场景、处置、解法创作；
- 标准案例提议、GREEN、readiness 与发布。

如果 Codex 说“没有规则编写入口”，先检查 `.codex/config.toml` 的 `enabled_tools` 是否包含 `rg.journey.start`、`rg.journey.next`、`rg.library.overview.get`、`rg.capability.search`、`rg.feature.handoff`、`rg.scenario.define`、`rg.instruction.define`、`rg.solution.compose` 和 `rg.solution.golden.propose`，并确认 Header 为 `BUSINESS_SOLUTION`，然后彻底重启 Codex。不要让小李补写 DSL。

## 4. 开场约定

小李在新的 Codex 任务中输入：

```text
你是我的业务工具搭建助手。

我只负责说明业务目标、判断依据、规则和标准答案。请你使用已经连接的业务工具平台，自行完成能力发现、契约设计、实现草稿、检查和修正。

和我沟通时只使用业务语言，不展示代码、配置、数据结构、内部标识或技术诊断。收到业务目标后先启动一条新的业务旅程；每次继续前读取平台给出的当前阶段、阻塞原因和允许动作，只在允许范围内推进。缺少业务含义时可以问我一个明确问题；缺少系统实现时请建立工程交接，不要让我提供技术方案。每完成一幕就停下来让我核对。不要替我批准标准答案，不要替我签署上线，也不要发布未经签署的内容。

请用一句话复述我们的分工，然后等我提出业务目标。
```

正确回应应说明：小李负责业务真相和上线决定，Codex 负责技术翻译与平台操作。

## 5. 第一幕：盘点业务能力库并定义业务事实

这一幕不是一次性填写表单。小李分多轮表达业务意图；Codex 每轮只收敛一个事实定义，并把当前理解反馈给小李。事实含义未确认前，Codex 不提交含糊契约，也不把技术选择包装成业务决定。

### 第一轮：提出目标并盘点能力库

#### 小李输入

```text
我是网约车业务的客服政策负责人。

我想把“取消费纠纷怎么处理”做成客服助手可以直接使用的业务能力。客服选择一个争议订单后，需要得到三种处置之一：全额免除取消费、维持原收费、转人工复核。

做判断至少需要知道两件事：这次取消主要由谁负责，以及订单是否仍在免费取消时段内。责任方可能是无人担责、司机、乘客或平台。订单由客服在当前会话中选择。

请先盘点当前业务能力库。业务含义完全一致的能力可以作为复用候选；业务含义还不清楚的，不要急着创建，请先问我一个最重要的业务问题。不要只凭名称相似就复用，也不要让我填写接口、数据结构或技术定义。

这一步只告诉我：已经存在的候选能力、确定缺失的能力，以及第一个需要我确认的业务口径。不要展示底层技术名称。
```

#### Codex 应反馈

- 当前会话需要「选择争议订单」「判断责任方」「判断免费取消时段」三项事实能力。
- 哪些库内能力只是名称相似，哪些经过契约比较后可以复用，哪些确定缺失。
- 首先询问「责任方」究竟以什么业务结论为准，以及无法取得结论时能否推断。

#### 平台验收观察点

- Codex 先按“事实”范围搜索三项判断依据，不在决策、处置或完整解法中混排候选。
- 第一次搜索只做候选发现。Codex 读取相关候选的完整业务说明，再用完整含义复核一次。
- 只有复核得到唯一可复用项时，Codex 才报告“可以复用”。候选业务口径不同或存在多个完全
  一致项时，只向小李提出一个业务问题。
- 投屏对话不出现类型参数、概念键、内部引用或查询结构；这些信息由 Codex 与平台自行处理。

### 第二轮：定义「责任方」

#### 小李输入

```text
「责任方」以客服处理这笔纠纷时，订单上最新生效的判责结论为准。结果只能是无人担责、司机、乘客或平台。

「无人担责」必须是明确的判责结论，不能把尚未判责、资料缺失或多个结论冲突当成无人担责，也不能根据是谁发起取消自行推断。无法得到明确结论时，这项事实应标记为不可用，自动处理必须停止并转人工确认。

请先用业务语言复述这项事实的含义、需要基于哪笔订单、可能结果和不可判断情形。只复述，不要开始设计规则；如果仍有业务歧义，只问一个问题。
```

#### Codex 应反馈

- 判断对象是客服当前选择的同一笔争议订单。
- 取值依据是最新生效的明确判责结论，不从取消发起方等旁证推断。
- 结果范围是无人担责、司机、乘客或平台；缺失、未生效或冲突时不产生替代值。
- 该事实需要平台稳定获取，业务定义明确后仍可能等待特征工程接入。

### 第三轮：定义「免费取消时段」

#### 小李输入

```text
「是否在免费取消时段内」判断的是取消发生当时，而不是客服现在处理工单的时间。应按这笔订单当时适用且已经生效的免费取消政策判断，结果只有「是」或「否」。

如果找不到取消发生时间、找不到当时适用的政策，或者政策存在冲突，就不能默认成「否」，也不能继续自动处理；应把这项事实标记为不可用并转人工确认。

请同样复述这项事实的判断时点、依据、可能结果和不可判断情形。如果定义完整，就进入三项事实的最终确认。
```

#### Codex 应反馈

- 判断时点是订单发生取消的时刻，不使用客服当前处理时间。
- 判断依据是该订单在取消时适用且已生效的免费取消政策。
- 结果范围是「是」或「否」；时间、政策缺失或政策冲突时不产生默认值。
- 该事实需要平台加工得出，业务定义明确后仍可能等待特征工程接入。

### 第四轮：确认三项事实并形成契约

#### 小李输入

```text
订单由客服在当前会话中明确选择。客服切换订单后，前一笔订单的责任方和免费时段结论不能继续使用，必须针对新订单重新取得。

请把我们刚才确认的三项事实整理成业务定义卡，再与能力库中的候选契约做一次精确比较。业务含义、所需上下文、可能结果、不可判断情形和取值责任全部一致时才可复用。

没有完全匹配的，就建立新的业务事实契约。需要系统获取或加工的事实请生成工程交接；由客服提供的事实保留为用户提供。最后只告诉我每项事实的业务定义、当前状态和下一责任方。
```

### Codex 后台应完成

- 创建本次变更的业务旅程。后续每项写入都携带同一旅程和当前 revision；不得凭提示词记忆跳过阶段。
- 先读取当前作用域的业务能力库概览；发现可能复用的能力时，再读取其当前业务契约。
- 从库概览提供的创作说明中自行生成 Feature、Scenario、Instruction 和 Solution 定义；这些说明只供 Coding Agent 使用，不向小李展示。
- 演示后可用 [真实 Codex 业务创作过程截图](acceptance/agent-tdd/business-solution-codex-certification-v1.png) 复盘完整链路；截图来自 payload-free 机器证书，不展示案例原文、内部参数或模型推理。
- 不能只凭名称相似复用。业务含义、所需上下文、可能结果、不可判断情形和取值责任必须全部一致。
- 每轮保留待确认的事实定义摘要；只有小李确认三项定义后，才写入或复用权威契约。
- 建立“责任方”“是否在免费取消时段”“当前选择的争议订单”三项事实契约。
- 将前两项确定性事实保持为设计态，并分别建立特征工程交接单。
- 将“订单选择”识别为人工交互事实，不伪造自动求值实现。
- 工程交接应携带已确认的业务含义、所需上下文、结果范围和不可判断约束。工程师只补获取或加工实现。
- 不创建第二套同义事实，不向小李展示内部引用。

### 三项事实的业务定义卡

| 业务事实 | 业务口径 | 可能结果 | 不可判断时 | 当前状态 | 下一责任方 |
| --- | --- | --- | --- | --- | --- |
| 选择争议订单 | 客服明确选择当前处理的订单；切换后重新取得其他事实 | 一笔明确订单 | 未选择时不进入自动处理 | 用户提供 | 客服 |
| 判断责任方 | 读取该订单最新生效的明确判责结论；不得从旁证推断 | 无人担责、司机、乘客、平台 | 缺失、未生效或冲突时停止自动处理 | 等待工程接入 | 特征工程师 |
| 判断免费取消时段 | 按取消发生时该订单适用且生效的政策判断；不使用当前时间 | 是、否 | 时间、政策缺失或冲突时停止自动处理 | 等待工程接入 | 特征工程师 |

### 后续处置的能力库盘点

| 业务能力 | 业务含义 | 当前状态 | 下一责任方 |
| --- | --- | --- | --- |
| 全额免除取消费 | 退款后回读确认取消费已免除 | 待业务定义 | 小李 |
| 维持原收费 | 给出维持结论，不修改业务系统 | 待业务定义 | 小李 |
| 转人工复核 | 创建工单后回读确认已进入人工队列 | 待业务定义 | 小李 |

这些表是业务能力与事实定义，不是技术组件清单。Codex 可以在后台读取算子契约，但不能向小李展示算子名称、binding、接口或 Schema。

### 本幕成功信号

- 观众看到小李通过多轮业务表达逐步确认事实，而不是一次提交技术表单。
- 小李看到三项事实的含义、判断时点、结果范围、不可判断处理和责任方。
- “责任方”“免费时段”显示等待工程接入；订单选择显示为用户提供；三种处置显示待业务定义。
- Codex 没有询问接口地址、字段类型、DSL 或 YAML。
- 若业务含义不完整，Codex 只问业务问题；若平台工具缺失，明确报平台维护待办并停止。

### 幕间停点：事实能力就绪

特征工程师履行交接后，Codex 必须重新读取业务能力库和两项事实的当前契约，并确认履约没有改变小李确认的业务定义。只有“判断责任方”和“判断免费取消时段”都显示已验证，才能进入规则设计。这里的“已验证”只证明获取实现可运行且结果符合契约形状；事实口径和整条政策是否正确，仍要由后续标准案例证明。仍未就绪或契约发生变化时应停止，并明确等待哪个责任方，不得用样例、固定值或同名能力替代。

## 6. 第二幕：工程履行事实，再由小李确认规则

幕间由保障人员按操作手册第 3.1 节履行两个特征交接。看板应把两项事实从“设计态”更新为“已验证/就绪”。Agent token 调同一履约地址必须得到 403。Codex 随后重新读取业务能力库和当前契约，再向小李确认规则设计可以开始。

### 小李输入

```text
事实来源已经由工程师接好了。请先重新读取三项事实的当前业务定义，确认责任方口径、免费时段判断时点、不可判断处理和订单切换规则都没有变化。任一项变化或仍未就绪时请停止，不要继续设计规则。

确认一致后，请按以下政策设计处理规则：

1. 无人担责，并且还在免费取消时段内：全额免除取消费。
2. 司机责任：维持原收费。
3. 乘客责任：维持原收费。
4. 平台责任：转人工复核。
5. 其他没有明确覆盖的情况：转人工复核，不能自动猜。

全额免除需要写入退款系统；转人工复核需要创建客服工单；维持原收费不改业务系统。每种处置都必须说明原因。

请自行形成可执行草稿并完成平台检查。先不要运行案例，也不要发布。完成后只用业务表格向我说明：每条规则会得到什么处置、哪些处置还等待工程实现。
```

### Codex 后台应完成

- 复核两项判断事实均为当前且已验证；任一项未就绪就停止，不进入规则编排。
- 对三项处置再次做精确复用检查；只有业务含义、结果和业务影响一致时才复用已有能力。
- 建立三项处置契约，并填写明确的业务名称；结果都包含处置结果与原因。
- “全额免除”和“转人工复核”保持设计态，声明下游与对账要求；“维持原收费”只复用平台已批准的只读实现。
- 建立含四条规则和兜底分支的场景，再组合为同一取消费解法。
- 对草稿执行服务端预检；技术错误由 Codex 根据安全诊断自行修正。
- 为两个设计态写处置建立一张写工程交接单，然后停止。

### 小李在看板核对

| 责任方 | 免费时段 | 业务处置 |
| --- | --- | --- |
| 无人担责 | 是 | 全额免除取消费 |
| 司机 | 任意 | 维持原收费 |
| 乘客 | 任意 | 维持原收费 |
| 平台 | 任意 | 转人工复核 |
| 其他 | 其他 | 转人工复核 |

本幕不能因为写实现尚未完成而让 Codex 自行填一个“看起来像”的实现引用。正确状态是“业务规则已形成，两个写处置等待工程履约”。

## 7. 第三幕：工程实现处置，业务给出标准答案

幕间由通用工程师按操作手册第 3.1 节履行退款与工单两项交接。交接单全部完成后应为 `IMPLEMENTED`，但尚未 `CLOSED`；只有真实写对账成功才能关闭。

### 小李输入

```text
写处置已经由工程师实现。以下四个案例是业务标准答案，不能为了迁就当前实现而修改：

1. 免费时段内且无人担责，应全额免除取消费。
2. 司机责任，应维持原收费。
3. 乘客责任，应维持原收费。
4. 平台责任，应转人工复核。

请把它们整理为待我确认的标准案例，并检查是否覆盖每条明确规则。不要替我批准，也不要开始真实写入。
```

### Codex 应完成

- 提议四条完整 GOLDEN 标准案例，分别保留小李给出的业务意图、给定事实、依赖结果假设、期望处置、解释类别和标准答案负责人。
- 标准答案保持独立，不根据实现结果改写。
- 平台把事实值、依赖返回值和预期结果写入加密 material；案例列表和 MCP 响应只显示计数、生命周期与指纹，不返回案例正文。
- 告诉小李需要到看板逐条确认，并停止在人工停点。

### 人工停点一：批准业务应然

小李在看板逐条打开详情，核对“前提事实、期望处置、业务意图、负责人”，再批准。审批期间如案例被修改，服务端拒绝旧 revision，必须刷新重审。

成功信号：四条案例均为 ACTIVE；Codex 不能用 Agent token 调批准接口；看板能在独立 HUMAN 会话中解密展示完整案例，业务 MCP 只能看到安全摘要；看板能显示规则矩阵、处置清单、事实卡和四条案例。

## 8. 第四幕：GREEN、受控写对账与上线签署

### 小李输入

```text

先验证业务规则对四个标准案例都成立。逻辑验证不能访问真实业务系统。逻辑通过后，由平台按批准案例在本地沙箱验证退款和工单写入，并回读确认结果一致。

```

### 平台应完成

- GREEN 逻辑验证中 `realExternalCalls=0`，四条案例均为 GREEN_PASS。
- 每条案例使用自己的受控事实和依赖结果；READ 与 WRITE 依赖都不能进入真实 channel。缺少假设时失败关闭，不回退到默认实现。
- 只有 `GREEN + GO + handoff=IMPLEMENTED` 时，平台才派生内部写权限。
- 平台只消费当前 ACTIVE GOLDEN，在本地 demo ledger 中执行退款和建单并回读。
- 对账为 RECONCILED 后，写交接单从 IMPLEMENTED 变为 CLOSED。
- 重复相同 GREEN 不重放 CLOSED 交接；过程丢失时返回 RECOVERY_REQUIRED，不自动猜测重试。

### 人工停点二：五面板审阅与签署

小李打开解法的业务审阅窗口，依次核对：

1. 规则矩阵；
2. 三项处置及写入影响；
3. 三项判断依据及来源状态；

5. 发布卡中的逻辑、实现、写对账和签署门。

## 9. 第五幕：发布、复用与运营回流

### 小李输入

```text
我已经在看板完成上线签署。请确认规则、标准案例、工程实现和对账证据从签署后都没有变化；全部一致时再发布。

发布后，请用“免费时段内且无人担责”的业务情形演示一次客服调用，并告诉我命中了哪条规则、得到什么处置。最后只汇报累计调用、规则命中、转人工比例和处置分布，不展示订单内容、认证信息或内部指纹。
```

### 成功信号

- 发布物类型为 Solution，旧签署不能授权变化后的实现。
- 调用前平台分别求值确定性事实并签名；篡改事实值时调用被拒绝。
- 正常调用得到“全额免除取消费”及业务原因。
- 相同幂等键重放同一结果，运营累计只增加一次。
- 运营看板能显示命中、升级、处置分布和政策缺口，但不保存订单、事实值、结果正文、原因或 token。

## 10. 技术幕后：业务能力如何落到算子库

本节只供保障人员和工程师使用，不投到业务画面，也不复制进小李的提示词。底层算子库只在这个幕后层出现。

| 业务人员看到的资产 | 平台中的职责 | 算子库与工程履约 |
| --- | --- | --- |
| 判断依据 | Feature：给规则提供可信业务事实 | 特征工程师把确定性判断绑定到求值算子；用户选择的事实继续由用户提供 |
| 业务规则 | Scenario：只根据事实决定处置 | 使用零外呼的纯决策算子，不承担退款或建单 |
| 业务处置 | Instruction：说明结果、原因和业务影响 | 通用工程师绑定写入与回读对账算子；无写入的处置保持纯函数 |
| 完整客服能力 | Solution：把判断、规则和处置组合成可复用解法 | 平台组合已验证契约，不绕过工程交接 |

多轮业务对话最终收敛为一份 Feature 契约。两者的对应关系如下：

| 业务对话确认的内容 | Feature 契约承载的内容 | 谁可以决定 |
| --- | --- | --- |
| 事实解决什么业务问题 | 业务含义 | 小李 |
| 判断基于哪笔业务对象 | 所需上下文 | 小李定义，Codex 结构化 |
| 可能得到哪些结果 | 原子结果范围 | 小李定义，Codex 结构化 |
| 由用户提供还是由平台稳定取得 | 取值责任与确定性 | 小李确认业务责任，Codex 选择契约形态 |
| 缺失、冲突或过期时怎么办 | 业务含义中的失败约束；求值失败时不生成默认事实 | 小李定义 |
| 具体从哪里读取、怎样计算 | 版本化实现引用 | 特征工程师履约，Codex 与小李不能填写 |

Codex 的后台顺序必须是：

1. 读取当前作用域的业务能力库概览。
2. 对可能复用的能力读取当前契约。
3. 通过多轮业务对话补齐事实含义、上下文、结果范围、不可判断处理和取值责任。
4. 精确比较业务含义、所需上下文、结果范围、不可判断处理和取值责任。
5. 对缺失能力建立设计态契约与工程交接，而不是猜实现。
6. 工程履约后重新读取能力库和当前契约，确认业务定义没有漂移。
7. 所有必需能力就绪后，才进入规则、案例和发布流程。

工程履约只能补实现，不能修改业务契约。Feature 或 Instruction 业务契约变化时，完整案例变为 `GOLDEN_CASE_STALE`，必须重新提议并批准；旧版明文或仅批准预期结果的案例变为 `LEGACY_GOLDEN_REAPPROVAL_REQUIRED`。实现绑定变化时，案例批准可以保留，但 GREEN 证据与上线签署必须失效并重新生成。

## 11. 主持人故障分流

| 现场表现 | 应停在哪一幕 | 处理人 | 不应做什么 |
| --- | --- | --- | --- |
| Codex 看不到规则/交接工具 | 会前 | 平台维护 | 让业务人员写 DSL |
| 找不到业务含义完全一致的能力 | 第一幕 | Codex/业务负责人 | 按名称猜着复用，或让业务人员设计算子 |
| 事实口径或不可判断处理仍有歧义 | 第一幕 | 业务负责人 | 先建一个含糊契约，等工程师自行解释 |
| 事实仍是设计态 | 第一幕 | 特征工程 | 用假数据、固定值或同名能力冒充已接入 |
| 工程履约后事实定义发生变化 | 第一幕 | 业务负责人/特征工程 | 沿用旧确认直接进入规则设计 |

| 签署后资产变化 | 第五幕 | 重新验证与签署 | 复用旧签署 |
