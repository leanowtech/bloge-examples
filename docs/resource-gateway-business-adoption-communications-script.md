# Resource Gateway 面向业务管理者的采用沟通讲稿

## 使用说明

- **适用对象**：业务负责人、运营负责人、产品负责人、风险与质量管理者。
- **建议时长**：12—15 分钟，另预留 10 分钟问答。
- **沟通目标**：降低业务管理者对 DSL、编码智能体和新工作方式的学习焦虑，说明业务控制权、采用路径和验证方式。
- **核心立场**：Resource Gateway 不要求业务人员成为开发者。平台承担技术复杂度，业务人员继续负责业务目标、规则边界、结果验收和发布批准。
- **贯穿案例**：客户资格策略需要增加主服务失败后的备用服务，并保留高风险人工确认。该案例用于说明工作方式，正式试点应替换为集团真实业务流程。

## 一句话定位

> 把复杂度留在平台，把业务控制权交还业务：业务人员通过表达目标、确认约束、查看差异和验收证据完成变更，无需直接编写 DSL 或操作底层系统。

## 对外沟通的四条边界

1. 不宣传「业务人员都要写代码」，应说明 DSL 是平台保存和验证业务资产的内部形式。
2. 不宣传「智能体自动决定业务」，应说明编码智能体负责生成候选方案，业务 Owner 负责业务判断和最终批准。
3. 不承诺未经验证的效率数字。试点前测量现状，试点后比较交付周期、人工步骤、返工、覆盖和事故风险。
4. 不要求一次性替换现有流程。先旁路观察，再生成草案，随后进入受控发布，最后才考虑扩大自动化范围。

## 完整口播稿

### 1. 开场：先正面回应采用顾虑

各位业务负责人，今天讨论 Resource Gateway，我想先回应一个最现实的问题。

把业务资产变成可版本化、可测试的资产，再引入编码智能体辅助工作，从技术视角看是一种进步；从业务团队视角看，也可能像一次过大的工作方式变化。大家自然会担心：是不是要学一套新语言？是不是原来的经验会失效？是不是以后要像研发团队一样工作？如果智能体生成错误内容，业务责任又由谁承担？

这些顾虑是合理的。如果一个平台把技术复杂度转嫁给业务人员，即使技术能力再先进，也很难形成稳定采用。

Resource Gateway 的产品目标因此很明确：**业务人员不学习底层语法，平台承担生成、转换和验证；业务人员继续掌握目标、约束、验收标准和发布决定。**

### 2. 业务责任保持不变，业务人员把时间投入到更有价值的判断

今天的一次业务规则变更，往往需要在多个页面之间查找入口、复制历史配置、理解字段含义、联系技术团队确认接口、准备测试数据、逐步试跑，再人工记录结果。

业务人员的大量时间消耗在机械操作和跨团队翻译，而非业务判断本身。

Resource Gateway 希望把工作调整为五个步骤：

1. 业务人员用熟悉的语言说明目标和适用范围。
2. 业务人员确认不能突破的规则、风险边界和验收条件。
3. 编码智能体检索已有业务资产，生成最小变更草案。
4. 平台自动执行结构检查、隔离测试和覆盖检查，并用业务可读方式展示结果。
5. 业务 Owner 查看差异、风险和证据，决定批准、退回或调整。

运营人员的角色由「配置执行者」逐步转为「业务资产负责人」。业务经验不会被削弱，而会成为系统需要遵守的约束和验收标准。

### 3. DSL 和编码智能体分别承担什么

DSL 可以理解为业务资产的标准保存格式。它让规则、流程、资源关系和验证场景能够被版本管理、比较、测试和回滚。

业务人员通常不需要直接阅读或编写 DSL。就像使用电子表格不需要理解文件内部格式一样，业务人员可以继续使用表单、模板、对话式入口和可视化差异。DSL 在后台确保同一项业务资产能够被系统准确保存和验证。

编码智能体也不是业务决策者。它承担的是检索、生成和修复候选方案：查找已有资源、理解 Schema、形成变更草案、补充测试场景、执行验证并根据失败诊断修改草案。

业务判断仍由业务 Owner 负责。哪些客户可以进入、哪些风险需要拦截、什么结果才算正确、哪项例外可以接受，这些都不能交给智能体自行定义。

### 4. 贯穿案例：一次客户资格策略调整

假设业务提出一项变化：客户资格判断依赖一个主数据服务。当主服务发生容量故障时，可以切换到备用服务；但涉及高风险客户时，系统不能自动放行，应进入人工确认。同时，这次变化需要保留完整的验证和发布记录。

在传统方式下，业务人员可能需要找到多个配置入口，确认主备服务参数，修改流程节点，准备不同故障数据，再协调技术和测试团队逐步确认。即使最后试跑通过，也很难快速回答：备用服务是否只在指定故障下调用？高风险分支是否一定进入人工确认？是否存在没有覆盖的业务条件？

使用 Resource Gateway 后，业务人员先表达三个业务事实：

- 主服务发生指定故障时允许切换备用服务；
- 高风险客户不能自动通过；
- 发布前需要证明关键分支已经覆盖。

编码智能体根据现有资产生成一份最小差异。业务人员看到业务可读的变化摘要：新增了什么条件、影响了哪些流程、哪些测试已经通过、哪些边界仍未覆盖。

平台在隔离环境中模拟主服务失败、备用服务成功、高风险拦截以及不应调用的路径。验证失败时，平台返回的是具体问题，例如「高风险条件未进入人工确认」或「备用服务在非指定故障下被调用」，而不是只给出一段技术错误。

当业务 Owner 确认差异、覆盖和风险均符合预期后，再批准发布。发布记录与准确的资产版本和验证证据绑定，后续可以回溯和回滚。

这个案例说明，新工作方式没有取消业务判断，而是让业务判断从口头约定和页面操作转为可复核的资产和证据。

### 5. 采用不会一步到位，而是分四个阶段推进

为了降低学习和业务连续性风险，建议采用渐进路径。

**第一阶段是旁路观察。** 现有流程不改变，Resource Gateway 只记录资产、依赖和变更步骤，帮助团队建立现状基线。业务人员不承担新的操作责任。

**第二阶段是智能草案。** 业务人员用模板或自然语言提出变更，智能体生成候选方案，但仍由现有流程完成最终变更。团队主要验证草案是否准确、解释是否清楚。

**第三阶段是受控发布。** 选择可隔离、可回滚的场景，让通过验证的资产进入正式发布流程。高风险变化保持人工审批，低风险变化也保留明确的回退方式。

**第四阶段是规模复用。** 只有在周期、返工、质量和风险指标得到证明后，才把成熟资产推广到更多场景和团队。

每个阶段都设置退出条件。业务价值没有改善、学习成本过高、证据不足或风险边界不清楚时，不进入下一阶段。

### 6. 产品需要主动承担学习成本

采用门槛不能只靠培训解决，产品本身需要承担四项责任。

第一，提供熟悉的业务入口。常见任务应通过表单、模板、业务术语和对话式描述完成，原始 DSL 只保留给专家路径。

第二，把技术差异翻译为业务差异。页面需要说明业务规则、影响范围、风险变化和验证结果，技术指纹和内部坐标放在核查区域。

第三，按风险分层。草案、内部验证、受控发布和高风险审批使用不同门槛，避免所有变化都进入同样沉重的流程。

第四，保留现有流程和回滚。试点期间不取消原有能力，任何正式变更都绑定准确版本、审批记录和回滚条件。

### 7. 角色如何变化

业务人员负责目标、约束、业务 Oracle 和发布批准。这里的业务 Oracle，是指业务能够明确判断「什么结果算正确」的规则和示例。

编码智能体负责检索已有资产、生成最小差异、补充验证场景和根据诊断修复草案。

平台与研发团队负责运行时、连接适配、权限、隔离、工具链和稳定性，不要求业务人员理解底层实现。

质量与风险团队负责覆盖政策、风险分级、证据要求和例外管理。

责任不会因为引入智能体而消失。相反，每个角色的输入、判断、批准和结果都更加清楚。

### 8. 如何判断试点是否值得继续

我们不预设效率提升数字。试点开始前先记录当前基线，再观察五类指标：

- 从提出意图到形成可验证发布候选的周期；
- 业务人员完成一次变更需要经历的人工步骤和等待时间；
- 草案被退回、人工修订和重复沟通的次数；
- 关键业务条件的覆盖情况，以及仍未覆盖的分母；
- 生产误触、未授权写入、回滚和事故风险。

这里最重要的指标是「可验证业务资产交付周期」：它同时约束速度和正确性。只提升生成速度、却增加风险和返工，不算成功。

### 9. 结尾：今天需要批准什么

今天只需要考虑一个可控试点，不涉及全面转型，也不要求所有运营人员学习新工具。

建议只批准一个可控试点：选择一个高变更、多依赖、可隔离、可回滚的业务流程；指定业务 Owner；记录现有周期、人工步骤和质量基线；先从旁路观察与智能草案开始。

业务团队负责判断价值，平台团队负责吸收复杂度，质量与风险团队负责守住边界。只有当业务人员感受到操作减少、判断更清楚、结果更可信时，才进入下一阶段。

Resource Gateway 希望推动的变化可以概括为一句话：**让业务人员少做配置，多做判断；让系统少依赖经验，多依赖可验证证据。**

## 30 秒摘要

Resource Gateway 不要求业务人员学习编程。业务人员仍然用熟悉的方式表达目标、确认规则、查看差异和批准发布；DSL 负责把业务资产标准化保存，编码智能体负责生成候选方案，确定性工具负责验证。采用从旁路观察开始，经过智能草案和受控发布，在业务指标和风险证据成立后才扩大范围。我们希望减少机械配置和重复沟通，同时强化业务 Owner 的控制权。

## 推荐传播短句

- 把复杂度留在平台，把业务控制权交还业务。
- 业务人员少做配置，多做判断。
- 智能体生成候选方案，业务 Owner 定义正确结果。
- 先旁路观察，再生成草案；先证明价值，再扩大范围。
- 每次业务变化都有差异、有验证、有责任人、有回滚。

## 不建议使用的表达

- 「让业务人员像程序员一样工作。」
- 「智能体自动完成所有运营工作。」
- 「不再需要技术团队或测试团队。」
- 「业务规则可以零风险自动发布。」
- 「DSL 本身就是竞争壁垒。」
- 「一次性完成业务工作方式转型。」

## 常见问题与建议回答

### 1. 业务人员需要学习 DSL 吗？

不作为默认要求。常见任务通过表单、模板、对话式入口和业务差异视图完成。DSL 是平台内部保存、比较、测试和回滚业务资产的标准形式，专家仍可使用 DSL 处理复杂情况。

### 2. 这会不会增加业务人员的工作量？

试点初期会增加目标、约束和验收标准的显式确认，但应减少查找配置、重复录入、准备测试、跨团队解释和人工留痕。如果总工作量没有相对基线改善，试点不应扩大。

### 3. 编码智能体生成错误内容怎么办？

智能体只生成候选变更，不能绕过 Schema、隔离测试、覆盖检查、权限和人工门禁。验证失败会返回具体业务影响，正式发布仍由授权角色批准。

### 4. 是否意味着减少运营岗位？

当前目标是减少机械配置和重复协调，把时间转向业务规则、例外管理、结果验收和持续改进。岗位与编制变化属于独立的组织决策，不由技术平台自动决定。

### 5. 谁对最终业务结果负责？

责任边界保持明确：业务 Owner 负责业务目标、规则和批准；平台团队负责系统能力；质量与风险团队负责验证政策与例外；所有动作保留版本和证据。

### 6. 现有系统和流程是否需要替换？

不要求一次性替换。Resource Gateway 与现有 API Gateway、工作流、业务系统和集成平台组合。试点先以旁路方式建立资产和证据，再决定哪些步骤适合迁移。

### 7. 低风险的小变化会不会被治理流程拖慢？

产品采用风险分层。草案、内部验证、低风险发布和高风险审批使用不同门槛。治理要求需要与业务风险相匹配，并通过周期和返工指标持续校准。

### 8. 如何保护敏感业务数据？

测试控制与业务输入分离，测试应在隔离环境运行，不触碰未授权生产凭据、网络或写型资源。Evidence 以版本、覆盖和验证事实为主，不应包含凭据或业务 payload。

### 9. 多久能看到效果？

不预设统一时间或收益。建议选择 90 天内能够发生一次真实变更、同时可隔离和回滚的场景，在试点前建立基线，在真实变更后评估是否继续。

### 10. 第一批适合什么场景？

优先选择高变更、多依赖、跨系统、失败成本较高且能够隔离回滚的流程。不优先选择一次性项目、简单页面配置或无法明确业务 Owner 和验收标准的场景。

## 试点决策请求

1. 选择一个真实、可隔离、可回滚的业务流程。
2. 指定业务 Owner、平台 Owner 和质量／风险负责人。
3. 授权采集当前周期、人工步骤、返工和质量基线。
4. 先运行旁路观察和智能草案，不直接替换生产流程。
5. 以业务指标、采用反馈和风险证据决定是否进入受控发布。
