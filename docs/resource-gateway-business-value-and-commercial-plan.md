# Resource Gateway 业务价值、商业价值与商业计划书

> 版本：决策草案 v1.0
>
> 日期：2026-08-16
>
> 依据：Resource Gateway 当前实现与设计文档，以及 [同类理念与解决方案市场研究](research/resource-gateway-solution-landscape.md)
>
> 适用对象：集团决策层、技术委员会、业务平台负责人、商业化负责人、风险与质量负责人
>
> 事实边界：本文没有使用未经验证的市场规模、价格、客户数量或收入预测。涉及阶段、门槛和产品包装的内容均为建议方案，需要通过集团内部试点和外部设计伙伴验证。

## 1. 执行结论

市面上尚未发现与 Resource Gateway 完整设计理念和产品定位相同的成熟产品，这是一项积极信号，但不能单独证明商业机会成立。

市场空白通常存在四种解释：

1. 需求真实，但现有产品把能力分散在 iPaaS、工作流、API 管理和测试平台中，尚未形成统一产品。
2. 技术与使用方式刚刚成熟，业务资产 DSL 化、编码智能体和验证工具开始具备组合条件。
3. 客户认可问题，但采购预算、产品类别和责任部门尚不清楚，难以形成独立市场。
4. 需求规模不足，或解决方案的部署、治理和连接器成本超过客户愿意支付的价值。

结合当前产品能力和市场研究，本计划书的判断是：

> Resource Gateway 具备值得集团投资验证的商业化选择权，但目前仍是「有差异化的产品能力假设」，尚未成为「被客户、价格和交付模型证明的商业机会」。

建议集团批准一个有明确退出条件的商业验证计划，而不是立即按成熟产品投入规模化销售和交付资源。

### 1.1 建议决策

| 决策项 | 建议 | 原因 |
| --- | --- | --- |
| 是否继续投入 | 有条件继续 | 技术差异清楚，市场趋势与产品方向一致 |
| 是否立即独立商业化 | 暂不 | 买方、预算、价格和复制性交付尚未验证 |
| 第一市场 | 集团内部高风险、高变更、多资源编排场景 | 可以获得真实基线、运行证据和组织协同条件 |
| 第一产品楔子 | 「可验证业务资产交付」而非通用 iPaaS | 避免与连接器规模和低代码画布正面竞争 |
| 第一阶段投入方式 | 90 天商业验证 + 6 个月灯塔场景 | 用证据控制继续投入、扩围或停止 |
| 外部市场动作 | 选择少量设计伙伴共同验证 | 先证明付费问题和交付复制性，再建设销售体系 |

## 2. 为什么「没有成熟同类产品」不能直接等同于机会

商业机会至少需要同时满足五项条件。

| 条件 | 需要回答的问题 | 当前证据 | 结论 |
| --- | --- | --- | --- |
| 问题强度 | 客户是否为此持续付出人力、周期、事故或合规成本 | 仓库设计回应了复杂集成、测试隔离和证据治理问题 | 技术证据较强，客户量化证据不足 |
| 买方与预算 | 谁拥有问题、谁能批准采购、预算来自哪里 | 可能涉及平台、质量、风险和业务运营多个部门 | 尚未确认单一经济买方 |
| 产品替代性 | 客户能否用现有 iPaaS、工作流、脚本或人工流程解决 | 市场研究显示能力分散，完整正确性链缺失 | 存在差异，但组合替代方案很多 |
| 交付复制性 | 新客户是否无需大量定制即可获得价值 | Descriptor 和通用 Operator 有利于复制 | 企业身份、网络、KMS/HSM 和业务 Oracle 仍需集成 |
| 单位经济性 | 客户价值是否显著高于软件、实施和运营成本 | 可以建立价值公式 | 缺少真实基线和付费验证 |

因此，市场空白只能作为「进入验证」的理由，不能作为「扩大投入」的理由。下一阶段需要证明客户问题、产品价值、付费意愿和可复制交付同时成立。

## 3. 已经具备的机会基础

### 3.1 Resource Gateway 已形成完整的产品循环

当前仓库已经形成三个连续动作：

1. 通过 `ResourceDescriptor` 和 Schema 把外部 API 转为稳定业务资源。
2. 通过 `.bloge` Graph、决策、转换和子图组合业务资产。
3. 通过 Contract、Scenario、Fixture、Coverage 和 Evidence 验证并发布资产。

所有内置资源主要通过通用 `HttpResourceOperator` 执行，避免为每个供应商复制 Java Operator。这为降低新资源接入的边际成本提供了技术基础。[Resource Gateway README](../resource-gateway-examples/README.md#notice-the-product-loop)

### 3.2 可测试性已进入产品协议，而不是停留在测试脚本

Resource Gateway 将测试控制放在业务输入之外，并设计独立 test-runtime、测试身份、网络边界和证据存储。生产运行携带测试计划时，在节点调度前失败关闭。[ADR-001](adr/ADR-001-resource-gateway-test-runtime-isolation.md)

独立 Test Kit 不依赖 Resource Gateway Server 或 Spring Boot，以版本化 JSON Schema 为通信权威，可以执行测试、验证覆盖并离线复核签名证据。[Test Kit README](../resource-gateway-test-kit/README.md)

这意味着产品具备将「正确性证明」建设成独立可销售能力的基础，而不仅是附带一个测试按钮。

### 3.3 市场趋势支持业务资产 DSL 化与编码智能体运营

市场研究确认了多个相邻趋势：

- Camel MCP、Tray Headless、MuleSoft Vibes、Kestra、n8n CLI 与 Agent Skill 已把机器可读资产、验证工具和编码智能体连接起来。
- Camunda、MuleSoft、Azure Logic Apps 和 Google Application Integration 已证明业务 DSL 可以进入版本、Mock、测试、Coverage 或 CI 流程。
- Temporal、LangSmith、Dagster 和 Apicurio 分别证明稳定执行、评估数据集、资产检查和版本兼容治理具有独立价值。

这些事实不能证明客户一定购买 Resource Gateway，但说明产品所依赖的工作方式已经进入市场，不需要从零教育客户理解 DSL、编码智能体和验证资产。

## 4. 核心业务价值

### 4.1 将运营人员从重复配置转向意图与验收

传统运营工作通常包括查找配置入口、理解字段、复制已有流程、手工连接节点、准备测试数据、逐步试跑和人工记录结果。系统升级或人员变化后，这些隐性知识容易丢失。

业务资产 DSL 化后，运营工作可以调整为：

`表达业务意图 → 确认约束和业务 Oracle → 审阅 Agent 生成的资产差异 → 查看隔离测试和覆盖缺口 → 批准发布`

编码智能体可以承担目录检索、Schema 查询、连接器研究、草案生成、局部修改、静态校验、测试执行和失败定位。运营人员保留业务预期、高风险接受和发布批准责任。

对应价值指标包括：

- 单次业务规则变更的人工操作步骤；
- 从意图提出到可验证草案的周期；
- 首次验证通过率；
- 每次变更的人工修订次数；
- 自动生成测试被业务人员接受的比例；
- 高风险变更进入人工确认的比例。

所有指标均需要在试点前测量基线，不预设收益数字。

### 4.2 把业务资产纳入成熟软件工程体系

当 Resource Descriptor、Graph、Contract、Scenario 和 Fixture 成为可版本化文本资产后，可以直接复用以下方法：

- Git、Diff、代码评审和责任人机制；
- Schema 校验、静态分析和兼容性检查；
- 单元测试、表格测试、故障注入、回归测试和变异测试；
- CI 门禁、发布记录、回滚和版本影响分析；
- 过程度量、缺陷归因和持续改进。

业务资产由此从「页面中的配置记录」转为「有合同、有测试、有责任人、有证据的工程资产」。

### 4.3 降低复杂集成的变更成本

通用 Operator 与声明式 Descriptor 将变化尽量收敛在合同和资产层。新供应商、新版本或新业务组合不再天然要求复制完整运行代码。

建议观察：

- 新资源从需求到首次可运行的周期；
- Descriptor 与现有 Operator 的复用比例；
- 每个新资源新增的专用代码量；
- 上游 API 变化后的受影响资产定位时间；
- 同一资源在不同业务 Graph 中的复用次数。

### 4.4 提高变更正确性和风险可控性

Resource Gateway 的价值不止是让测试数量增加，而是回答以下问题：

- 测试替换了哪一层外部效应；
- 真实执行了哪些 Graph 和 Operator 逻辑；
- 哪些业务事实、边界、重试、降级和异常仍未覆盖；
- 测试是否可能触碰生产凭据、网络和写型资源；
- 当前 Evidence 是否仍与目标版本、计划和 Fixture 匹配；
- 第三方能否在不依赖服务端实现的情况下复核证据。

建议观察：

- 生产触碰与测试污染事件数量；
- 变更逃逸缺陷率；
- 关键业务事实覆盖率及其未覆盖分母；
- Evidence 完整率和过期率；
- 回归失败平均定位时间；
- 高风险写操作的协议与审计覆盖率。

### 4.5 形成集团级可复用业务资产

集团价值来自跨团队复用，而不是单个项目减少几次配置。

可复用对象包括：

- Resource Descriptor 与认证、参数、错误协议；
- 通用 Operator 和 Function；
- 业务 Graph、Decision 与 Mapping；
- Contract、Scenario、Fixture 与 Coverage Policy；
- 经过验证的 Evidence 和兼容性结论；
- 行业场景包、运营模板和编码智能体 Skill。

建议观察：

- 跨团队复用的资产数量和调用范围；
- 重复集成数量；
- 新业务域采用已有资产的比例；
- 资产从首次建设到第二次复用的时间；
- 单个新增场景的边际交付成本。

## 5. 商业价值主张

### 5.1 推荐产品定位

推荐将 Resource Gateway 定位为：

> 面向复杂企业业务的可验证资源编排与正确性治理平台。

更完整的客户表述是：

> 将外部 API、业务规则和测试场景转为可版本、可复用、可由编码智能体维护的业务资产，并以隔离测试、语义覆盖和独立证据控制变更风险。

### 5.2 不建议使用的定位

- 「新一代 API Gateway」：会被客户按流量治理、吞吐和插件数量比较。
- 「通用 iPaaS」：会被客户按连接器数量、SaaS 覆盖和低代码画布比较。
- 「工作流引擎」：会被客户按长流程、人工任务和持久化调度比较。
- 「AI 自动配置工具」：容易把确定性治理能力压缩成一次生成演示。
- 「测试平台」：会丢失业务资产、运行时和复用价值。

### 5.3 客户购买的结果

客户购买的不是 DSL 语法或架构图，而是以下结果：

1. 更快交付可验证的业务资源变更。
2. 降低复杂集成中的生产副作用和回归风险。
3. 让业务运营、安全、质量与开发围绕同一资产和证据协作。
4. 将已有业务知识沉淀为可以跨团队复用的资产。
5. 让编码智能体在可审查、可测试和可授权的边界内进入运营流程。

## 6. 目标客户与第一产品楔子

### 6.1 理想客户特征

优先选择同时满足以下条件的企业或集团业务域：

- 一个业务结果依赖多个内部系统、外部 API 或供应商；
- 上游接口、规则或供应商组合经常变化；
- 失败会导致资金、客户权益、合规或重大运营损失；
- 当前变更依赖大量页面配置、脚本、人工试跑和跨团队协调；
- 已有 API Gateway、iPaaS 或工作流平台，但缺少统一的业务正确性证据；
- 具备平台工程、质量治理或风险治理负责人，可以承担跨部门赞助。

不优先选择简单网站集成、低风险个人自动化、一次性交付项目或只追求连接器数量的客户。

### 6.2 购买与使用角色

| 角色 | 主要诉求 | Resource Gateway 提供的价值 |
| --- | --- | --- |
| 经济买方：集团 CIO、CTO 或业务平台负责人 | 跨域复用、交付效率、风险和平台投资回报 | 资产目录、统一运行与集团治理 |
| 业务赞助人：业务运营、产品或风险负责人 | 更快修改业务规则，同时保留业务控制权 | 意图、Oracle、Diff、证据和发布批准 |
| 技术使用者：平台与集成工程师 | 减少重复 Operator 与脆弱脚本 | Descriptor、通用 Operator、Graph DSL |
| 质量与风险使用者 | 知道证明了什么、缺什么、能否晋级 | Scenario、Coverage、Evidence、独立验证 |
| 安全与运维团队 | 测试不触碰生产，权限和网络可审计 | 独立 test-runtime、Purpose、Identity、Egress Control |

### 6.3 第一灯塔案例

建议继续使用仓库中已经具备的「主信用服务失败后切换备用服务」场景作为技术基准，再选择一个集团真实业务流程作为商业灯塔。

真实灯塔场景需要满足：

- 有明确业务 Owner 和现有流程基线；
- 同时包含多资源调用、规则判断、重试或降级；
- 至少包含一个不允许误调用的外部效应边界；
- 能在 90 天内完成一轮真实变更；
- 结果可以用周期、人工步骤、缺陷、覆盖和证据衡量；
- 失败时可以回滚，不影响关键生产链路。

## 7. 产品结构与商业包装

### 7.1 建议产品结构

| 产品能力 | 解决的问题 | 商业化角色 |
| --- | --- | --- |
| Resource Registry | 资源身份、Schema、版本、Owner 和依赖不可发现 | 平台基础 |
| Graph Authoring | 业务资源组合、决策、转换和复用 | 业务资产生产入口 |
| Stable Runtime | 统一执行、预算、重试、降级和副作用协议 | 生产运行基础 |
| Test Control Plane | Fixture、故障、Replay、隔离运行和批量回归 | 核心差异能力 |
| Coverage & Evidence | 事实分母、指纹、签名证据和独立复核 | 治理与合规价值 |
| Agent Tooling | Catalog 查询、ChangeSet、验证、测试和诊断 | 运营效率增长层 |
| Enterprise Integration | IAM、KMS/HSM、网络、审计、数据驻留和多租户 | 企业采购必备能力 |

### 7.2 建议开放与收费边界

建议采用「开放协议和开发者入口 + 商业化企业控制面」的方向，但在完成设计伙伴验证前保留最终许可选择。

建议开放或公开可验证：

- Resource Descriptor、Graph Contract、Scenario 和 Evidence 的 Schema；
- 通用 Runtime 的基础能力和本地开发体验；
- Test Kit 的协议兼容与独立验证能力；
- OpenAPI、Arazzo、MCP、Camel/Kamelet 等互操作接口；
- 基础示例、CLI 和编码智能体 Skill。

建议商业化：

- 多租户企业 Registry 与资产生命周期治理；
- 独立 test-runtime 的规模化调度、配额和数据隔离；
- IAM、Purpose、策略、审批、KMS/HSM 和审计集成；
- Evidence 保留、跨环境晋级、策略门禁和舰队管理；
- 企业支持、SLA、升级兼容和部署认证；
- 行业资产包、实施方法和合作伙伴工具。

独立验证协议不宜完全封闭。客户只有能够在服务端之外验证 Evidence，才会相信它可以作为发布或审计依据。

### 7.3 自建、合作与不进入的边界

| 策略 | 能力 |
| --- | --- |
| 核心自建 | Resource Descriptor 语义、业务 Graph 合同、测试隔离、Fixture 保真度、Semantic Coverage、Evidence 和 Agent 治理 |
| 优先合作 | Camel/Kamelet 连接生态、OpenAPI/Arazzo、MCP、Backstage、现有 API Gateway、工作流和云连接器 |
| 采购集成 | 企业身份、KMS/HSM、Secret、日志、对象存储、策略引擎和可观测平台 |
| 暂不进入 | 大规模连接器市场、通用长流程引擎、全功能 API Gateway、通用低代码页面搭建 |

## 8. 商业模式假设

### 8.1 收入结构

建议验证以下组合，不建议按单个 Connector 收费：

1. **年度平台订阅**：按企业环境、业务域和治理能力分级。
2. **规模用量**：按受治理资产、测试执行或运行规模设置阶梯，而不是惩罚资产复用。
3. **企业能力包**：IAM/KMS、数据驻留、审计、舰队管理和高级 Evidence。
4. **行业资产包**：经过验证的 Descriptor、Graph、Scenario 和政策模板。
5. **专业服务**：灯塔实施、资产迁移、平台集成和团队训练；长期需要控制占比，避免产品退化为项目制。

### 8.2 定价原则

- 价格应与「受治理业务变化的价值和风险」相关，而不是与画布节点数量相关。
- 基础开发体验需要降低试用门槛，企业治理与规模运行承担主要收入。
- 不对独立验证和客户数据可移植性设置锁定障碍。
- 服务报价需要明确标准实施边界，超出部分单独评估。
- 在三家以上设计伙伴验证预算归属前，不公布正式价格体系。

### 8.3 价值测算公式

内部或客户年度价值可以按以下方式测量：

```text
年度效率价值
= 年度业务资产变更次数
  ×（当前单次变更工时 - Resource Gateway 单次变更工时）
  × 综合人力成本

年度质量价值
= 避免的生产缺陷数量 × 单次缺陷期望损失
  + 缩短的故障定位时间 × 事故相关人力成本

年度复用价值
= 被复用的资源/Graph/Scenario 数量 × 替代的重复建设成本

年度经营价值
= 上线周期缩短带来的经业务方确认的增量收益

净价值
= 年度效率价值 + 年度质量价值 + 年度复用价值 + 年度经营价值
  - 软件订阅 - 实施成本 - 基础设施成本 - 持续运营成本
```

任何商业案例都需要由财务、业务和平台共同确认输入，不能只使用技术团队估算。

## 9. 市场进入策略

### 9.1 第一步：集团内部验证「可验证业务资产交付」

集团内部不是免费试用环境，而是第一位严格客户。需要建立基线、服务目录、Owner、SLO 和成本归集。

目标是证明：

- 运营人员确实减少机械配置和跨团队沟通；
- 编码智能体生成的 ChangeSet 可以被确定性工具收敛；
- 业务 Oracle、覆盖缺口和 Evidence 能成为发布决策的一部分；
- 新业务场景可以复用已有资产，而不是继续定制；
- 平台价值大于建设和运营成本。

### 9.2 第二步：外部设计伙伴

选择少量具备真实问题、技术团队和决策赞助人的设计伙伴。设计伙伴需要同意提供：

- 当前变更流程与成本基线；
- 一个可隔离、可回滚的真实场景；
- 业务 Owner、平台 Owner 和质量/风险参与人；
- 对产品边界、采购流程和付费意愿的真实反馈；
- 在约定范围内可公开的匿名化案例证据。

设计伙伴不是免费定制客户。任何专属需求都需要判断是否进入通用产品，避免同时形成多条客户分支。

### 9.3 第三步：行业解决方案与合作伙伴

当两个以上客户复用同一类 Resource、Graph、Scenario 和治理政策后，再形成行业资产包。系统集成商、API 管理厂商、质量平台和云市场可以成为渠道或交付伙伴。

进入渠道前需要具备：

- 标准部署与升级路径；
- 明确许可和价格；
- 客户数据与 Evidence 责任边界；
- 合作伙伴认证与兼容测试；
- 可重复的实施周期和验收清单。

## 10. 分阶段商业化路线

### 阶段 0：90 天机会验证

**目标**：证明问题、买方、价值基线和第一场景成立。

**关键动作**：

- 访谈业务、平台、质量、风险和财务角色；
- 选择一个集团真实灯塔场景；
- 记录当前流程、工时、缺陷、发布和事故基线；
- 建立 Resource Gateway 目标流程和最小产品差距；
- 形成内部价值测算和外部设计伙伴名单。

**退出条件**：

- 有明确经济买方和业务 Owner；
- 有可在 90 天内运行的灯塔场景；
- 当前问题有可量化基线；
- 关键企业集成差距和成本可估算；
- 至少有外部设计伙伴愿意进入严肃验证，或明确确认采购问题。

任一核心条件长期不成立，应缩小定位或停止独立商业化假设。

### 阶段 1：3—6 个月灯塔验证

**目标**：证明产品能改变真实工作流程，并产生可复核价值。

**建议门槛**：

- 测试运行不得触碰未授权生产凭据、网络或写型资源；
- 所有发布候选均可追溯到准确资产版本和验证证据；
- 关键业务事实、未覆盖分母和 Waiver 对决策者可见；
- 业务变更周期、人工步骤或返工中至少一项相对基线显著改善；
- 平台团队能够在不创建客户专属运行分支的情况下交付场景。

「显著改善」的具体阈值由阶段 0 的基线和集团投资要求共同确定。

### 阶段 2：6—12 个月产品化验证

**目标**：证明第二场景、第二团队和第二部署可以复用。

**关键动作**：

- 完成独立 test-runtime 与企业身份、网络、KMS/HSM 集成；
- 抽取独立产品包，降低对示例工程的耦合；
- 建立升级、兼容、支持和事故响应流程；
- 验证同一资产包跨两个业务域复用；
- 与外部设计伙伴验证部署、采购和价格。

**退出条件**：

- 至少两类真实场景复用稳定产品能力；
- 新场景交付不依赖核心团队逐项手工修改；
- 产品支持和基础设施成本可测量；
- 设计伙伴愿意为明确能力范围承担预算；
- 安全、法律和许可问题没有阻断项。

### 阶段 3：12—18 个月规模化选择

**目标**：决定集团平台化、独立商业化、合作输出或停止扩张。

可选路径：

1. 集团内部平台：以内部效率、风险和复用价值为主要回报。
2. 企业软件产品：建立订阅、支持和行业解决方案体系。
3. 与现有平台联合：将 Evidence/Test Control Plane 作为能力层嵌入 iPaaS、API 管理或工作流生态。
4. 开放协议与工具：扩大生态影响力，商业化企业治理服务。
5. 停止独立产品：若买方或单位经济性不成立，将能力保留为集团技术资产。

## 11. 关键指标体系

### 11.1 北极星指标

推荐使用「可验证业务资产交付周期」作为北极星指标：

> 从业务意图被接受，到形成带准确版本、业务 Oracle、覆盖结果和可复核 Evidence 的发布候选所需时间。

该指标同时约束效率和质量，避免只追求生成速度或测试数量。

### 11.2 指标分层

| 层级 | 指标 |
| --- | --- |
| 业务结果 | 业务变更周期、目标达成、事故损失、客户或运营结果 |
| 运营效率 | 人工步骤、等待时间、返工次数、首次验证通过率、Agent 建议接受率 |
| 工程质量 | Contract 通过、关键事实覆盖、Mutation、Fixture Fidelity、Evidence 完整率 |
| 风险治理 | 生产触碰、未授权写、Waiver 数量、证据过期、审计发现和恢复时间 |
| 平台复用 | Descriptor/Graph/Scenario 复用率、新场景边际成本、跨域采用数量 |
| 商业健康 | 设计伙伴转付费、年度合同价值、实施周期、毛利、续约和支持成本 |

不得使用一个综合分数隐藏各维度分母和风险债务。

## 12. 竞争策略与可持续优势

### 12.1 不参与连接器数量竞赛

MuleSoft、Workato、Boomi、云厂商和 Pipedream 已经具备大规模连接生态。Resource Gateway 应通过 OpenAPI、Camel/Kamelet 和现有平台连接能力，集中建设正确性与治理层。

### 12.2 DSL 本身不是壁垒

DSL 语法容易被模仿。可持续优势需要来自以下累积：

- 经过真实业务验证的 Resource、Graph、Scenario 和 Fixture 资产；
- 精确版本、兼容和跨环境晋级协议；
- Fixture 保真度、Semantic Coverage 和签名 Evidence 方法；
- 客户身份、网络、KMS/HSM 和审计系统的可信集成；
- 编码智能体使用过程产生的失败语料和确定性反馈；
- 跨业务域复用形成的资产网络效应；
- 独立 Test Kit 与合作伙伴兼容认证形成的生态信任。

### 12.3 推荐竞争姿态

- 与 Camel/OpenAPI/MCP 合作，扩大资产和 Agent 生态。
- 与 API Gateway、iPaaS 和工作流系统组合，避免替换客户全部基础设施。
- 用「可以证明什么」区分普通设计器、试跑和日志平台。
- 用集团真实场景和独立验证证据建立可信案例，不依赖演示视频。

## 13. 主要风险与应对

| 风险 | 早期信号 | 应对 |
| --- | --- | --- |
| 市场空白实际来自需求不足 | 访谈认可理念但无人提供场景、预算或 Owner | 停止扩大平台，保留内部能力 |
| 产品类别和经济买方不清 | 平台、质量、风险和业务相互转交预算 | 以具体业务结果发起灯塔，建立联合预算 |
| 产品边界过宽 | 同时追逐 Gateway、iPaaS、工作流、画布和 AI 平台 | 固定「可验证业务资产交付」楔子 |
| 连接器生态冷启动 | 每个客户都要求大量专用集成 | 优先 OpenAPI/Camel 投影和客户自助 Descriptor |
| 正确性治理过重 | 低风险变更绕开平台或交付周期变长 | 按风险分级门禁，保留快速草案与渐进验证 |
| Agent 生成不稳定 | 变更 Diff 大、返工多、Oracle 被模型臆造 | 限定 Agent 工具、最小 Diff、确定性验证和人工 Oracle |
| 企业集成成本过高 | IAM、网络、KMS 和数据驻留占据主要交付周期 | 形成标准适配层、认证清单和合作伙伴能力 |
| Evidence 被误当成业务真相 | 技术签名有效但业务权威事实缺失 | 保留外部业务权威验证和明确 abstention |
| 开放后被成熟厂商复制 | 大厂增加 DSL、Mock 和 Agent 功能 | 积累业务资产、验证协议、部署证据和生态兼容 |
| 项目制侵蚀毛利 | 收入依赖核心团队长期驻场 | 标准实施边界、伙伴交付和产品化退出门槛 |

## 14. 组织与治理建议

第一阶段不需要先建立完整商业部门，但需要一支跨职能产品小组：

- 产品负责人：负责客户问题、定位、场景和阶段门槛；
- 架构与运行负责人：负责 Descriptor、Graph、Runtime 和企业集成；
- 测试与证据负责人：负责 Scenario、Coverage、Evidence 和独立验证；
- 开发者与运营体验负责人：负责 Authoring、Agent Tooling 和工作流；
- 业务 Owner：定义意图、业务 Oracle、风险和价值基线；
- 商业化负责人：负责设计伙伴、采购、价格和渠道验证；
- 安全、法律与财务代表：按阶段参与身份、数据、许可和价值审查。

治理机制包括双周产品证据评审、月度商业假设评审和阶段退出评审。评审对象是基线、运行事实、客户承诺和成本，不是功能完成数量。

## 15. 集团决策层需要批准的事项

1. 将 Resource Gateway 定义为集团级「可验证业务资产」能力方向，允许开展商业验证。
2. 指定一位集团业务或平台高层作为经济赞助人。
3. 选择一个真实灯塔场景，并授权获取现有周期、工时、缺陷和事故基线。
4. 批准 90 天机会验证；在阶段退出评审前，不启动大规模销售与连接器建设。
5. 要求平台、业务、质量、风险、财务共同确认价值和风险口径。
6. 允许接触少量外部设计伙伴，验证采购问题和付费意愿。
7. 以证据决定继续、调整定位、合作输出或停止，不以已投入成本推动扩围。

## 16. 下一步行动清单

### 决策后 10 个工作日内

- 确认赞助人、产品负责人和灯塔业务 Owner；
- 选定候选场景和备选场景；
- 建立价值基线模板和数据权限；
- 明确试点生产隔离和回滚边界；
- 确认外部设计伙伴筛选条件。

### 30 天内

- 完成业务、平台、质量、风险和财务访谈；
- 形成当前流程价值流和成本基线；
- 明确最小产品差距、企业集成差距和试点计划；
- 形成第一版内部价值测算；
- 完成潜在设计伙伴问题访谈。

### 90 天内

- 提交机会验证报告；
- 提交灯塔实施计划和安全评审；
- 提交商业包装、价格假设和设计伙伴承诺；
- 对照退出条件提出继续、调整或停止建议。
