01 · 业务洞见

客服组织真正稀缺的资产，是对跨域客户问题的可验证理解

事业部掌握订单、地图、支付和风控等局部事实；客服组织负责把分散事实组织为客户问题、处置策略和结果判断。这部分认知决定服务能力的上限。

01

接口接入逐渐成为基础能力

API 解决“能否调用”，无法独立回答“何时调用、为何调用、结果是否解决客户问题”。长期价值继续向跨域语义、状态和结果迁移。

02

客服拥有跨域问题模型

单一事业部通常不拥有取消费申诉、计价争议或重复扣款的完整解释。客服对事实的组合和处置，构成独特业务资产。

03

运行自主需要事实校准

客服可以脱离真实接口完成日常设计和回归，同时保持与真实业务真值的周期性连接，避免 Fixture 形成历史幻觉。

客服业务的目标，不是复制每个事业部的系统，而是形成能够解释跨域问题、独立演练解决方案、并持续用真实结果修正的客户业务模型。

05 · 业务产研协作

07 · 契约与正确性工作台

让业务人员按“定义边界、准备业务世界、声明正确答案、运行取证”完成闭环

工作台不要求业务人员直接维护一团原始 JSON。系统把稳定接口、数据来源、本次测试世界、正确性判断和运行证据拆成五种对象，并在同一任务流中保持引用关系。

BINDING数据从哪里来调用方、上游边、Context 或运行时资源
FIXTURE本次业务世界是什么外部返回、时间、身份、状态、故障和消费次数
ASSERTION什么才算正确路径、Schema、错误、状态迁移与治理预期
EVIDENCE哪次运行证明了什么冻结修订、Trace、差异、限制与证据等级

08 · 首个验证场景

以“乘客取消费申诉”验证从 L0 能力到 L3 服务的完整闭环

该场景跨越订单、地图、计费、支付、风控和城市政策，包含查询、资金副作用、时间规则、状态冲突和人工升级，复杂度足以暴露平台真实能力。

为什么选它

业务问题清晰、Outcome 可观察、风险可控，并且能够同时验证业务人员建模、产研绑定、状态与幂等、服务载体复用和只读真实校准。

首轮范围控制先覆盖文本机器人和镜像演练。语音识别、打断、静默和延迟等渠道变量在业务语义闭合后加入。
ORDER查询行程与取消事件
MAP司机到达与定位置信度
PRICING计费明细与规则版本
PAYMENT扣款、退款、冲正与重复支付
POLICY / RISK城市政策、身份与风险限制
EFFECT退款、补偿与工单事务回执

合法收取与司机未到达

验证系统能够区分合法费用和应退费用，既不错误退款，也不让合法申诉被规则默认值吞掉。

关键事实到达时间、距离、等待时长
关键动作解释、免除或退款
核心断言责任判断和金额一致

定位漂移与司机主动取消

多个事实相互冲突或定位置信度不足时，系统需要拒绝武断归责，并进入补充判断或人工接管。

关键事实轨迹冲突、定位置信度
关键动作拒答、补充查询、人工升级
核心断言未知不被解释为否定

重复扣费、支付冲正与重试

验证退款和补偿动作的幂等、未知提交和重复请求保护，避免“接口超时”被错误理解为“业务未执行”。

关键事实支付流水、冲正和事务回执
关键动作退款、查询、补偿
核心断言不重复退款，提交状态可证明

地图、支付或订单数据不可用

外部依赖超时或部分数据缺失时，流程应明确降级、保留限制并选择允许的 fallback，不用默认值制造确定答案。

关键事实缺失来源、错误类型、重试次数
关键动作fallback、接管、稍后处理
核心断言部分失败语义完整

城市政策和规则版本变化

系统按事件时间选择规则版本。任何策略修订都会使受影响场景和旧证据失效，并触发影响分析和重新演练。

09 · 度量与证伪

用业务结果和学习质量判断方向，而不是用资产数量自我证明

第一条纵向切片需要同时验证业务人员是否能使用、协作摩擦是否下降、复杂缺陷是否被发现，以及模拟与真实结果是否逐步收敛。

业务自主性无真实接口可完成的设计和回归比例同时报告最近校准时间和保真限制
协作效率能力缺口到可执行规格、接受到一致实现的周期避免只把等待转移到另一个团队
业务覆盖风险加权场景、状态、错误和策略覆盖Case 数量不能充当覆盖分母
保真运营Shadow 差异、stale debt、abstention debt 和修复时间不能删除难例来降低债务
真实结果错误处置、重复退款、人工纠正和二次申诉代理指标不能冒充权威 Outcome
业务人员能够生产可执行规格失败信号：大多数任务仍由研发代写 Schema、DSL 和 Fixture。
可执行规格能够降低协作摩擦失败信号：流程增加了文档工作，但澄清和返工没有下降。
镜像演练能够提升服务正确性失败信号：只增加测试数量，没有发现组合、状态或异常缺陷。
真实校准能够控制模型漂移失败信号：模拟长期全绿，真实差异和客户 Outcome 没有改善。
停止条件：如果约定验证周期结束后，业务人员仍无法独立维护候选规格，或 Shadow 差异无法形成可修复的模型改进任务，应暂停跨域扩张，回到工具门槛、资产语义和 Owner 机制重新设计。具体周期由项目治理评审确认。
10 · 演进与决策

从一个业务域的完整证据链开始，再复制到更多问题域

扩围依据是业务人员可运营、产研可一致实现、模拟可真实校准和资产可持续维护，不以模块开发完成或演示页面可用作为唯一判断。

STAGE A

冻结领域语义

确定业务一等对象、场景分母、Owner、事实来源和规格权边界。

STAGE B

业务自验证

图形化创建候选算子，在 `SIMULATION_ONLY` 环境运行完整流程。

STAGE C

产研一致实现

生成 runtime port 和测试，绑定实现并处理 typed diff。

STAGE D

真实校准

接入只读 Shadow 和 Outcome，运营 Fidelity 与 Drift。

STAGE E

跨域规模化

复制到计价争议、重复扣款、失物找回和司机服务投诉。

建议本轮冻结的管理决策

Resource Gateway 的长期定位是业务能力镜像与服务演练运行时。
`DomainCapabilityPackage` 是业务主对象，Graph 是执行投影。
业务拥有规格权，产研承担实现责任，治理系统裁决发布。
模拟、实现、校准和认证采用分级状态，不得互相冒充。
首个纵向切片选择“乘客取消费申诉”，先覆盖文本机器人。
覆盖采用风险加权场景分母，保真采用多维向量和未知债务。

进入实施前需要回答

  • `DomainCapabilityPackage` 的最终业务 Owner 由谁承担？
  • 事业部最小校准责任包含契约变化、Replay、Shadow 和 Outcome 中的哪些组合？
  • 取消费申诉的权威 Outcome 如何分层定义？
  • 业务人员首轮可以修改 Fixture、决策规则、候选契约和 Graph 中的哪些层级？
Resource Gateway 的长期价值，在于把客服对客户业务的理解转化为可运行的组织能力。业务理解越深、场景分母越完整、真实校准越持续，这套资产的复制成本越高。
