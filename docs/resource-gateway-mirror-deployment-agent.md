# Mirror deployment-isolation trust agent

This guide defines the deployment-side trust refresh boundary for Resource Gateway Mirror. It
connects the protected authority/attestation distribution APIs to a crash-safe local read-only
snapshot without giving the runtime network credentials, TLS private keys, or permission to choose
its own trust.

The implementation is reusable Java infrastructure. Certification-required Mirror execution now
double-observes one stable decision around the run and holds an agent read permit through evidence
transaction completion. Routine refresh may advance the local cache generation only while the
authority, attestation, and status decision remains exact.

## 1. What is implemented

| Component | Responsibility |
|---|---|
| `HttpMirrorDeploymentIsolationTrustSource` | Strict vendor-JSON GET over private-PKI, SPKI-pinned, identity-bound mTLS |
| `MirrorDeploymentIsolationTrustAgent` | Non-TOFU bootstrap, anti-rollback transitions, active dual verification, denial-first revocation |
| `AtomicFileMirrorDeploymentIsolationAgentCache` | Single-writer CAS, file force, required atomic rename, directory force, strict restore |
| `MirrorDeploymentIsolationAgentSnapshotIntegrity` | Nested canonical verification and complete snapshot fingerprint |
| `resourceGateway.mirrorDeploymentIsolationAgentSnapshot.v1` | Portable read-only cache protocol for runtime consumers |
| `AgentBackedMirrorDeploymentIsolationRunTrustAuthority` | Admission, terminal confirmation, stable-decision comparison, and commit permit |
| `resourceGateway.mirrorDeploymentIsolationRunTrust.v1` | Double-observed binding signed into Mirror evidence v2 |

The source reuses the existing generic `ControlPlaneHttpTransport` boundary. Production composition
must use a descriptor with all of the following:

- deployment-owned private trust store;
- normal PKIX and hostname verification;
- explicit server SPKI pinning;
- client-certificate mutual TLS;
- exact client and server X.509 workload-identity policy;
- redirects disabled.

System roots, TLS without client authentication, an unpinned server, or an unbound certificate
identity are rejected before the first request.

## 2. Trust and data flow

```text
operator security channel
  -> bootstrap roots + exact expected binding + exact initial floor

deployment agent
  -> GET current attestation bundle over pinned identity-bound mTLS
  -> if ACTIVE: GET its exact current authority publication
  -> verify root threshold, authority chain/floor, scope, deployment, policy, key and time
  -> verify attestation signature, deployment identity and current time
  -> enforce contiguous attestation/status transition
  -> write and fsync complete next snapshot
  -> atomic rename + directory fsync

runtime consumer
  -> admit one ACTIVE snapshot before durable request claim
  -> execute under the stable attestation-bundle decision
  -> confirm the same decision after execution; a newer local generation is allowed
  -> sign admitted and committed snapshot refs into Mirror evidence v2
  -> hold an agent read permit until evidence transaction completion
  -> never performs remote I/O
```

The control-plane GET routes require both:

```http
Accept: application/vnd.bloge.mirror-deployment-isolation-trust.v1+json
X-BLOGE-Mirror-Trust-Protocol: mirror-deployment-isolation-trust-v1
```

They still require normal `MIRROR_TRUST_DISTRIBUTION` or `MIRROR_REHEARSAL` workload
authentication. `RequestHeadersProvider` is invoked for every exact URI so nonce, timestamp and
request signatures are never cached as static configuration.

## 3. Why bootstrap is not TOFU

An empty cache cannot infer whether a valid-looking response is the true current head. The operator
must provision `TrustPolicy` through an independent security/configuration channel:

- complete expected enterprise scope;
- immutable deployment identity;
- key-set id, attestation issuer and root trust domain;
- root threshold and accepted policy fingerprints;
- independent bootstrap-root public keys;
- exact authority generation and publication fingerprint;
- exact attestation revision and fingerprint;
- exact local status revision and fingerprint.

The first remote response must equal all six floor coordinates. Fetching the floor from the same
HTTP response, environment variable generated by that response, or cache directory is TOFU and is
not an accepted deployment procedure.

After bootstrap, the durable cache is the local floor. Authority publications must be the same
generation or one signed predecessor-linked successor. Attestations must be the same exact revision
or the next revision. Local status may be the same exact value or the one permitted
`ACTIVE -> REVOKED` successor. The same attestation revision can never become active again.

## 4. Assembly

The following abbreviated composition shows the ownership boundaries. Password references must be
resolved by the deployment secret provider; raw passwords do not belong in application properties.

```java
ControlPlaneHttpTransport transport =
        new PinnedMutualTlsRecoveryFleetPublicationTransport(
                transportSettings,
                secretResolver);

var source = new HttpMirrorDeploymentIsolationTrustSource(
        objectMapper,
        Clock.systemUTC(),
        transport,
        new HttpMirrorDeploymentIsolationTrustSource.Settings(
                URI.create("https://resource-gateway.internal"),
                "deployment:staging",
                "mirror-isolation-authorities:staging",
                "mirror-staging-isolation",
                Duration.ofSeconds(2),
                4 * 1024 * 1024,
                false),
        (operation, uri) -> authorization.headersFor("GET", uri, operation));

var cache = new AtomicFileMirrorDeploymentIsolationAgentCache(
        Path.of("/var/lib/resource-gateway-agent/isolation-trust.json"),
        objectMapper,
        snapshotIntegrity);

var agent = new MirrorDeploymentIsolationTrustAgent(
        Clock.systemUTC(),
        source,
        cache,
        snapshotIntegrity,
        authorityIntegrity,
        bundleIntegrity,
        attestationIntegrity,
        trustPolicy,
        new MirrorDeploymentIsolationTrustAgent.Settings(
                Duration.ofSeconds(15),
                Duration.ofSeconds(60),
                Duration.ofSeconds(30)));

var runTrust = new AgentBackedMirrorDeploymentIsolationRunTrustAuthority(
        agent,
        Clock.systemUTC());
```

The public constructor starts one daemon refresher after validating any durable cache generation.
`refreshNow()` is available for startup probes and deterministic orchestration. `close()` stops only
background refresh; it does not delete evidence or trust state.

## 5. Cache filesystem contract

Provision the parent directory before starting the agent:

```bash
install -d -m 0700 -o resource-gateway-agent -g resource-gateway-agent \
  /var/lib/resource-gateway-agent
```

The cache path must be absolute, the parent must already exist and must not be a symlink, and an
existing target must be a regular non-symlink file. On POSIX filesystems each new generation is
created with owner read/write permissions only.

Replacement is deliberately strict:

1. read and independently verify the complete current snapshot;
2. compare its fingerprint with the writer's expected fingerprint;
3. require `candidate.cacheGeneration = current + 1`;
4. serialize and bound the complete candidate;
5. write a temporary file in the same directory and force it;
6. require an atomic replace operation; no non-atomic fallback is attempted;
7. force the parent directory;
8. read back and independently verify the committed generation.

A stale writer, unsupported atomic rename, malformed current file, oversized file, symlink target,
or failed force is a fail-closed cache error. Temporary orphan files are never authoritative because
readers open only the configured final path.

## 6. Revocation and availability semantics

ACTIVE and REVOKED intentionally behave differently:

| Event | Agent action | Runtime effect |
|---|---|---|
| Valid unchanged ACTIVE | Re-verify authority and attestation; refresh complete snapshot deadline | Positive use remains available |
| Valid successor ACTIVE | Require contiguous attestation revision and authority floor | New complete generation becomes active |
| Valid REVOKED successor | Verify canonical bundle and status transition without fetching positive authority | Denial is atomically committed immediately |
| Same revision reactivated | Reject | Existing revocation remains authoritative |
| Remote timeout/5xx | Keep prior bytes; record degraded refresh | Prior ACTIVE works only until `validUntil` |
| Protocol, signature, fork or scope error | Reject candidate; keep prior bytes | Same hard deadline applies |
| Cache corrupt or expired | Fail closed | No positive execution admission |

There are two useful bounds:

- normal observation bound: `refreshInterval + up to two requestTimeouts` because ACTIVE refresh may
  fetch an attestation bundle and its exact authority publication;
- hard missed-revocation exposure bound: `maximumSnapshotAge`; an old ACTIVE snapshot is unusable at
  or after its exclusive `validUntil` even if the control plane remains unavailable.

`maximumSnapshotAge` must cover one normal refresh attempt and must be chosen from the security SLO,
not from a desire to mask outages. A cached REVOKED generation stays a denial after its freshness
deadline; expiry never turns denial into permission.

## 7. Health and alerting

`agent.observation()` is fixed-cardinality and omits scope ids, cache paths, fingerprints,
certificates and payloads. Important states are:

| Status | Meaning | Alert/action |
|---|---|---|
| `BOOTSTRAPPING` | No accepted cache generation yet | Block runtime readiness; inspect floor and source auth |
| `ACTIVE` | Current active snapshot and latest refresh succeeded | Healthy |
| `ACTIVE_REFRESH_DEGRADED` | Prior active generation is still inside hard age after a failed refresh | Page before `validUntil` |
| `REVOKED` | Current exact artifact is denied | Keep runtime blocked; issue a new attestation revision to recover |
| `EXPIRED` | Positive cache age or signed lifetime closed | Block runtime and restore distribution |
| `CACHE_INVALID` | Local file failed strict parsing or fingerprint checks | Quarantine cache; recover from operator floor and audited source |
| `CLOSED` | Agent refresh stopped | Runtime must not treat this as ready |

Export counters for refresh success/failure and gauges for cache generation, authority generation,
attestation revision, status revision, `validUntil`, refresh interval, maximum snapshot age and mTLS
identity-binding readiness. Do not label metrics by tenant, deployment, attestation id or
fingerprint.

The integration capability probe additionally separates `mirrorServing` from
`mirrorIsolationRunTrustReady` and `mirrorCertifiableEvidenceServingReady`. An exploratory runtime
may remain available while certification fails closed during agent bootstrap, revocation, expiry,
or refresh outage.

## 8. Rotation, outage and recovery runbook

### Normal authority rotation

1. Publish the next predecessor-linked authority generation.
2. Issue the next attestation revision using a key active in that generation.
3. Wait until agent observations report the expected authority and attestation revisions.
4. Retire old authority keys only after fleet convergence and maximum snapshot age have elapsed.

### Emergency revocation

1. Revoke the exact current attestation with its status optimistic fence.
2. Monitor agent status moving to `REVOKED` within the configured convergence SLO.
3. Verify runtime admission is denied before repairing positive trust.
4. Issue a new contiguous attestation revision; never mutate or reactivate the revoked revision.

### Corrupt or lost cache

1. Stop the local runtime consumer and agent writer.
2. Preserve the corrupt file and operation logs for incident analysis.
3. Obtain a new exact bootstrap floor through the independent operator security channel.
4. Remove or quarantine the final cache file; never promote a temporary orphan.
5. Restart the agent, force `refreshNow()`, and verify the committed generation and health.
6. Re-enable runtime only after the next execution-admission integration gate passes.

### Prolonged control-plane outage

An ACTIVE runtime naturally stops when its cache deadline closes. Do not extend
`maximumSnapshotAge` during the incident unless security governance explicitly accepts the larger
missed-revocation window. A REVOKED cache remains safely denied and can wait for service recovery.

## 9. Verification delivered

Focused tests cover:

- real private-CA TLS with server SPKI pinning, client certificate authentication, and exact client
  and server SPIFFE identity policy;
- strict media negotiation, envelope field set, payload fingerprint and dynamic-header ownership;
- exact non-TOFU bootstrap, rollback/fork/gap rejection and contiguous successor acceptance;
- denial-first revocation while positive authority reads are unavailable;
- prevention of same-revision reactivation;
- bounded degraded ACTIVE use and hard expiry;
- atomic file persistence, owner-only permissions, CAS, generation continuity, strict restart,
  corruption, truncation, unknown fields, oversize and symlink rejection;
- JSON Schema packaging in the independent test-kit.
- same-decision refresh across increasing local generations;
- terminal decision-change rejection and complete execution-window coverage;
- a real read/write-lock race proving refresh cannot cross the evidence commit permit;
- durable request admission/attempt recovery and independent v2 evidence verification.

## 10. Runtime certification boundary delivered

Certification-required runs now enforce:

1. admission before durable request acquisition;
2. stable decision identity in request idempotency and lease-local snapshot identity in `TrustAttempt`;
3. terminal re-observation of the same decision with monotonic local generation;
4. complete authority/attestation/status coverage of the execution window;
5. v2 evidence carrying both admitted and committed snapshot references;
6. commit-time agent permit held through transaction completion;
7. crash/takeover recovery that cannot finalize under a different decision.

See [Mirror runtime trust binding](resource-gateway-mirror-runtime-trust-binding.md) for protocol,
error, migration, capability, and runbook details. Remaining production work includes multi-node
revocation-convergence certification, customer PKI/KMS/IdP and database HA/DR exercises, managed
clock controls, and a fixed non-Java v2 compatibility fixture.
