# Resource Gateway 演进为「客户业务世界模型 / 拟真」基础设施 — 详细技术方案

## 术语表

| 术语 | 含义 |
|---|---|
| **世界模型 (ResourceWorldModel)** | 针对某个客户/租户、长期积累且版本化的资产，用来描述"这个客户的外部世界（它依赖的各个外部 API）在各种条件下会返回什么"。 |
| **世界切片 (WorldSlice)** | 世界模型的一个实现单元，对应某个外部服务商的某个 API 版本。世界模型 = 若干切片的组合。 |
| **世界片段 (World Fragment)** | 一个世界切片的"行为"，用 BLOGE 自己的纯逻辑原语写成的纯函数：给定当前世界状态与一个请求，算出响应（以及可能变化后的世界状态）。 |
| **逻辑资源契约 (Logical Resource Contract)** | 一个与 API 版本无关的资源契约，只描述"这个资源在业务意义上收什么、给什么、成功/失败如何判定"。 |
| **剧情 (Scenario)** | 在某个世界模型之上跑的一段业务剧情：一组业务输入 + 期望系统据此应得出的结论。 |
| **执行模式 (ExecutionMode)** | 一次外部调用在测试/模拟时"以何种方式执行"的枚举（详见正文）。 |
| **证据 (Evidence)** | 一次运行产出的、不含业务负载的事实记录（每个节点执行了什么、命中了哪条 mock、断言结果如何），用于审计与回归。 |

## 第一部分 · 背景与目标

### 1.1 业务背景

客服（外包 / BPO 型）业务的服务质量上限，取决于一件事：**你对所服务客户的业务，理解得有多准、复现得有多真**。客户的业务规则、它依赖的外部系统的行为，如果你能高保真地在自己这边复现出来，你就能在不打扰客户、不依赖客户不稳定接口的前提下，验证规则、演练变更、复盘线上问题。

因此，一套能够做到下面两件事的技术架构，是这门生意长期竞争力的底座：

1. **积累拟合数据**：把"客户的外部世界在各种情况下会怎样反应"这件事，沉淀成可复用、可版本化的数字资产；
2. **基于拟合数据模拟运转**：用这份资产驱动业务规则跑起来，而**不强依赖**客户那些真实、多变、受限、甚至还没就绪的外部 API。

### 1.2 Resource Gateway 今天是什么

Resource Gateway 是一套基于 BLOGE 编排框架构建的服务。它表面上像一个 BFF（面向前端的聚合网关），但本质是"**把一次外部调用彻底声明化，再用一张编排图把多次调用与业务规则串起来，并且自带一个与生产隔离的确定性测试引擎**"。它当前有三层：

- **资源层**：一次外部 HTTP 调用被声明成一个"资源描述符"——URL 模板、方法、默认头、鉴权方式、超时、参数如何从业务输入映射到 path/query/header/body、如何从响应判定成功（HTTP 状态码、或响应体里的某个字段、或一段表达式）、如何从响应里提取业务负载。这些描述符集中登记在一个注册表里。有一个**通用**的 `httpResource` 算子，运行时按 id 取出描述符，完成"求值映射 → 渲染 URL → 合并头 → 真正发请求 → 校验响应 → 提取负载"的全过程。关键点：**发起外部调用的业务逻辑是声明式的、集中的、可复用的**，而不是散落在各处的手写代码。

- **编排层**：用一套 DSL（`.bloge`）把资源调用和业务规则编成一张有向图，图里可以有转换（transform）、决策表（decision-table）、条件分支、重试、兜底、补偿等原语。还有一个可视化画布，允许作者拖拽算子、连线，甚至引用"只声明了接口、还没实现"的算子。

- **执行控制层**（这是本方案的地基，且已相当成熟）：有一个**与生产完全隔离**的测试引擎——它复用不可变的算子绑定，但不共享生产环境的任何缓存、限流、熔断、持久化。测试时用一个"装置包"来驱动：装置包里已经把两类东西干净地分开了——**"外部世界返回什么"（fixtures）** 和 **"系统据此应该得出什么"（expect 断言）**。对于外部调用，它已经支持三种不同深度的替换：直接给最终解释好的输出、给原始响应让真实的响应协议去解释、只替换网络传输而让描述符内部逻辑照常跑。此外还有确定性的时钟/随机数/ID（固定种子），以及一个独立的客户端测试库（用 JSON Schema 作为通信契约）。

一句话概括现状：**"如何模拟一次调用"这件事，基础设施已经很扎实了**。

### 1.3 目标

把 Resource Gateway 从"一套很强的接口编排 + 测试工具"，演进为"**客户业务世界模型 / 拟真基础设施**"：让业务规则能基于合法定义的算子、函数与拟合数据**模拟运转**、脱离真实外部依赖；并把"拟合"本身沉淀为**可长期积累、可跨场景复用、可版本化**的业务资产。

**判断成功的客观标准：**
- 回归用例可以在**完全没有真实外部依赖**的情况下跑起来（所有外部调用都由世界模型来回答）。
- 当客户底层 API 升级时，**业务规则的测试几乎不需要改**（只需替换对应的一个"世界切片"）。
- 当你改动一条业务规则或一条资源契约时，能在**跑之前**就精确算出"哪些剧情会受影响"。
- 一个线上问题，能**一步**沉淀成一个可长期回归的剧情用例。
- 并且——因为这是一个"测试/拟真平台"——**平台自身的正确性是可证明、且能长期保持的**（这一条的重要性见第五部分）。

**明确不做的事**：暂不把这些能力抽象下沉为 BLOGE 框架级的通用扩展点（框架团队已把这件事排到后面，理由是语义尚未定型、过早下沉会把不成熟的约定固化成框架合同）；不改动对外的接口地址、图名、模块坐标；不破坏现有的 Java 25 预览特性构建。

## 第二部分 · 要解决的问题

### 问题一：两条模拟路径割裂，"脱离运行时"与"内部逻辑真跑"不可兼得

今天平台里有两套"模拟"能力，但它们互不兼容：

- 一套是**设计期模拟**：它能在算子还没实现的情况下把整张图跑起来，做法是把每个算子节点**整体**替换成"按输出 schema 合成的假数据"。代价是——**算子自己的逻辑从头到尾没有执行**，你验证不了"参数映射对不对、响应协议判定对不对、负载提取对不对"。
- 另一套是**治理级测试**：它能让算子的内部逻辑**真正执行**（只把最底层的网络传输换成桩），但前提是——**注册表里必须有这个算子的真实实现绑定**。

而业务真正需要的能力恰恰卡在两者中间：**既不部署具体算子实现，又要让边界算子（比如 `httpResource`）的内部逻辑完整跑起来并被验证**。这正是"基于合法算子库 + 测试数据模拟运行、不强依赖具体算子实现"这个诉求当前无法兑现的根因。

### 问题二：拟合数据没有可积累的一等抽象

现有的"装置包"是绑定在**某一次测试目标**上的——它是"为某个测试临时搭的台子"，用完这次就固定在那个目标的指纹上了。它不是"某个客户的外部世界在各种条件下的确定性行为"这样一份**可跨图复用、可长期演进、可版本化**的资产。因此"积累拟合数据"这件事今天**无处落脚**。

### 问题三：表达式函数无法脱离外部依赖模拟

算子层面的 mock 已经很完备，但**表达式函数**（业务规则里 `transform`、分支、决策所调用的函数）目前只能"真跑 / 观察 / 拒绝"，**不能注入返回值**。当一条业务规则依赖某个"包裹了外部查询"的函数时，你没法在脱离那个外部依赖的情况下模拟它。

### 问题四：线上问题无法沉淀为回归

"把线上问题变成一个回归用例"目前没有成型的通道。虽然底层有重放、录制语料等零件，但缺一条"从生产观测 → 生成拟合数据 → 固化为回归剧情"的闭环。

### 问题五：测试控制数据与业务数据在传输层混杂

今天发起一次测试调用时，"要注入什么 fixture、用什么模式跑"这类**控制数据**，和"业务输入是什么"这类**业务数据**，是混在同一个请求体里的。后果是：控制面的作用范围难以独立治理；要判断"这条流量是不是带了测试控制计划"，必须把请求体解析开才能知道——这让生产环境的安全隔离变得别扭。

### 问题六：拟合数据的真实性与合规脱敏的张力

世界模型的价值恰恰在于它能存**真实的外部响应数据**（这就是"拟合"）。但平台的证据体系是**刻意做成不含业务负载**的（为了审计与合规）。于是产生一个必须正面回答的张力：**真实业务负载到底合法地存在哪里、又如何不污染证据链和执行内核**。

### 问题七：测试资产与被测版本的绑定过脆

现有装置包用**精确指纹**把自己钉死在某个被测版本上。任何一点无关改动都会让它失效，而且完全没法跨 API 版本复用。这与"底层 API 升级不该误伤业务规则测试"的目标直接冲突。

### 问题八：生产环境的测试控制隔离

必须有一个经得起推敲的保证：**生产流量绝不会携带测试控制计划**，而且这个保证不能只靠单一环节——单点一旦失守就全线失守。

### 问题九（衍生，且最关键）：平台自身的正确性如何验证、并长期保持

这一条是我们要建的东西**本身就是一个测试/拟真平台**所带来的、绕不开的问题。一个测试平台如果自己有静默的 bug，它产出的每一个"通过 / 失败"都不可信——**这是比业务 bug 更危险的失效模式，因为它会污染所有结论且极难察觉**。而"如何验证平台自身正确、如何做系统级测试、如何让它在长期演进中保持可信"，是本方案必须作为一等公民来设计的，而不是事后补几个测试。

## 第三部分 · 解决这些问题能创造的价值

| 解决了什么 | 给业务带来什么 |
|---|---|
| 让边界算子在"不部署真实实现"时也能内部逻辑真跑 | 业务规则在真实算子还没就绪、或不可用时，就能被**完整**验证，迭代链路大幅缩短 |
| 让拟合数据成为可积累的一等资产 | 对客户业务的理解**可沉淀、可复利**，直接构成长期竞争壁垒 |
| 让表达式函数也能脱离外部依赖模拟 | 业务规则里"函数这条边界"也能被模拟，模拟覆盖不再有盲区 |
| 打通线上到回归的沉淀通道 | 线上问题**一次性固化**为回归用例，同类问题不复发 |
| 把控制数据与业务数据分开、把测试资产绑到"逻辑契约"而非具体版本 | 改业务规则时**回归范围精确可算**；客户 API 升级时**业务规则测试不被误伤** |
| 分级托管真实负载 + 生产纵深隔离 | 既能存真实拟合数据、又满足合规；生产环境的纯净有双重保障 |
| 把"平台自身可信"作为一等设计 | 平台产出的每一个结论都**可追溯、可证明**，长期演进不塌方 |

**归结成一句话**：把"对客户业务的理解"从口头经验，变成**可执行、可积累、可回归、可脱离真实依赖运转、并且平台自身可证明可信**的工程资产。

## 第四部分 · 解法设计

整套方案建立在两条贯穿始终的分离原则上，理解了它们，后面的每个设计都顺理成章：

- **机制与策略分离**：最核心的执行内核只负责产出"发生了什么"的**事实**（执行了哪种模式、命中了哪条 mock、得到什么 trace）。而所有的**业务与治理判断**（这次运行的证据算不算数、属于哪个租户、能不能晋升上线、生产要不要拦截）都放在内核之上的独立层里。业务概念绝不进入内核的数据类型——这样内核才可能被穷尽地、稳定地验证。
- **控制与数据分离**：这其实是把 BLOGE 框架自己的边界（业务数据属于图上下文、执行控制属于不可变的执行选项）一路延伸到网络传输层——**控制数据走独立的请求头，业务数据走请求体**。

在这两条原则下，方案分四层：治理层、资产层、机制内核、资源层。下面自底向上、逐个机制讲清楚。

### 4.1 统一的执行模式：让"脱离运行时"和"内部逻辑真跑"在同一条路径上

要消除第二部分说的"两条模拟路径割裂"，关键是承认一件事：一次外部调用在测试时"怎么执行"，其实由两个相互独立的问题决定——**在哪一层把真实换成假的**（直接给输出？给原始响应？只换网络？还是真发？），以及**被执行的"真逻辑"从哪来**（没有逻辑、纯按 schema 编？由描述符驱动、不需要部署实现？还是由已部署的算子实现驱动？）。

早期我曾想把这两个问题画成一张"二维正交表"，但很快发现它并不真正正交——大量组合是没有意义的（比如"直接给最终输出"时根本没有逻辑在跑，"真发网络"时又不可能凭 schema 编）。硬把它当二维表会让实现者造出一堆无意义的状态。所以我们改用一个**只枚举合法组合**的封闭集合，让非法状态在类型层面就无法被表达：

```java
enum ExecutionMode {
  PRIMITIVE_REAL,        // 纯逻辑原语(转换/决策表/分支)真跑，没有 mock 边界、也不需要绑定
  SCHEMA_STANDIN,        // 没有真实逻辑，输出直接按声明的输出 schema 合成
  DESCRIPTOR_PROTOCOL,   // 由描述符驱动，喂进原始响应，真实的响应协议与负载提取照常跑；无需部署实现
  DESCRIPTOR_TRANSPORT,  // ★地基：由描述符驱动，只把网络传输换成桩；参数映射/URL渲染/协议判定/负载提取全部真跑；无需部署实现
  BINDING_TRANSPORT,     // 由已部署的算子实现驱动，只换网络传输
  BINDING_REAL,          // 由已部署的算子实现驱动，真发网络（真集成）
  WORLD_DELEGATE         // 把这次边界调用，委托给"世界片段"（一段纯逻辑子图）去计算响应（世界模型跑起来时的形态）
}
```

其中 **`DESCRIPTOR_TRANSPORT` 是补上"两条路径中间那个缺口"的地基**：编译期由资源描述符加上一份传输层 fixture，临时组装出一个真实的 `httpResource` 算子（这正是现有传输桩机制在做的事），把它作为内核的一个正式档位。于是**没有部署任何算子实现，也能让 `httpResource` 的内部逻辑完整跑起来**。原来那条"整节点按 schema 合成"的设计期模拟，就成了 `SCHEMA_STANDIN` 这一档；两条老路径从此收敛进同一个内核。

**"这次运行的证据算不算数"不写进这个枚举**——它是治理层根据模式做的一个独立映射。这样内核保持纯粹，证据分级可以独立演化。映射关系是这样的（供治理层实现）：

| 执行模式 | 证据可信上限 | 为什么 |
|---|---|---|
| 按 schema 合成 | 探索级 | 没有任何真实逻辑跑过 |
| 描述符驱动（换协议 / 换传输） | 契约级 | 描述符逻辑真跑了，但不是已部署的真实实现 |
| 委托给世界片段 | 契约级 | 世界片段是纯确定的，但它终究不是真实外部 |
| 纯逻辑原语真跑 | 可参与认证 | 纯确定、可复现 |
| 已部署实现（换传输 / 真发） | 认证级 | 真实实现跑过，传输受控或真集成 |

### 4.2 逻辑资源契约：让"API 升级不误伤业务规则"有一个支点

要让"客户 API 升级时业务规则测试不用改"，需要一个**与版本无关**的中间层。我们引入"逻辑资源契约"——它只描述一个资源在**业务意义**上的样子：收什么、给什么、成功失败怎么判、是否幂等：

```java
record LogicalResourceContract(
    String contractId,           // 版本无关的逻辑 id，例如 "credit.getScore"
    SchemaEnvelope inputShape,    // 逻辑输入形态
    SchemaEnvelope outputShape,   // 逻辑输出形态
    ResponseSemantics semantics,  // 成功条件、错误分类、幂等性、可重试性等语义约定
    String contractFingerprint    // 结构指纹，用于判断"变了之后还兼不兼容"
) {}
```

业务剧情**绑定的是逻辑契约**；而具体的"某服务商某版本"的实现，去**满足**这个契约。于是客户 API 升级，本质就是"换一个实现、去满足同一个逻辑契约"，绑在契约上的业务剧情根本不动。

契约怎么来？——它是一个**独立的对象**（这样才能真正做到版本无关），但为了不让人从零手写，**它的初稿由现有的资源描述符自动投影生成**，再由人确认其中的业务语义。这样既零重复劳动，又保住了版本无关性。此外，当一个"实现"登记进来时，会**校验它产出的响应形态确实满足所声明契约的输出形态**，不满足就直接拒绝——避免"声称实现了某契约、却返回违约的数据"这种静默错误。

### 4.3 世界模型：用 BLOGE 自己描述"客户的外部世界"（自举）

这是整套方案里最关键的创新，也是"拟合数据成为一等资产"的落点。

一个客户的**世界模型**，是它的外部世界的确定性行为的集合，按"服务商 × API 版本"切成若干**切片**、长期积累、带版本：

```java
record ResourceWorldModel(String worldModelId, String tenantId, long revision, List<WorldSlice> slices) {}
record WorldSlice(String provider, String apiVersion, String logicalContractId, String contractFingerprint,
    BlogeFragmentRef behavior,   // “世界片段”：一段纯逻辑，(世界状态, 渲染后的请求) -> (新状态, 响应)
    StateSpec state) {}          // 为空表示无状态；否则声明状态键与默认初值
```

**每个切片的"行为"用什么写？——用 BLOGE 自己的纯逻辑原语写**（决策表 / 转换 / 分支）。这一步是刻意的"自举"：我们不去新造一门描述外部世界的小语言，而是复用编排框架已经有的、已经被充分测试过的、确定性的原语。它的好处是一箭三雕：

- **"这个请求匹配什么条件、返回什么"本来就是一张决策表**（默认行 + 若干条件覆盖行，按优先级确定顺序，出现歧义就直接失败）。于是"世界模型的匹配语言"自然就是决策表，全系统不需要第二套表达式语言。
- **有状态的世界**（比如"扣款之后再查余额要反映出变化"）也只是让这段纯逻辑去读写一份状态。状态本身由内核持有（每次剧情一份独立、单写者、确定性排序的状态存储，可序列化以便重放），而**这段纯逻辑只负责计算状态怎么变**——机制持状态、逻辑保持纯粹，两者干净分开。
- 它正是"别自己造 DSL"的正解：复用现成语言，不是绕过原则，而是对齐原则。

这段世界片段本身是一份**冻结、带指纹的 `.bloge` 工件**，登记时要过一个**纯净校验器**（强制它只用白名单里的纯原语，任何会产生副作用或去调真实外部的算子一律在创作期就被拒——这既保住"世界=确定性行为"这个不变量，也杜绝了"世界里又去调外部世界"的递归和 SSRF 风险），并且可以被**独立地单元测试**（给状态和请求、断言算出来的响应和新状态）。

需要强调：**这种"用框架原语描述世界"的自举，和"把能力下沉进框架"是两回事**——前者只是在应用层复用现成原语，后者才是那件被明确推迟的事，二者不冲突。

### 4.4 剧情与"编译下沉"：新抽象架在成熟机制之上，而不是取代它

一个**剧情**，是在某个世界模型之上跑的一段业务：一组业务输入，加上"系统据此应该得出什么"的期望断言。fixtures（世界怎么反应）与 expect（系统应得出什么）严格分开：

```java
record Scenario(String scenarioId, String tenantId, long revision, TargetRef target,
    WorldModelRef world, Map<String,Object> context,
    WorldStateInit stateInit /*可空，用来覆盖世界初值*/, List<Expectation> expect) {}
```

**资产层不取代已有的成熟机制，而是编译到它上面**：有一个"编译器"把 `(世界切片 + 剧情)` 编译成现有的装置包（外部行为 + 断言），并保留一份**可追溯的来源映射**（编译出来的每条 mock 规则，对应回世界里的哪条规则）。这样执行内核零改动，成熟的执行与证据机制被直接复用，风险最低。

这里有一个必须讲清楚的技术点：世界规则是挂在**逻辑契约**这个层级上的，而底层的 mock 规则历来是挂在**具体节点**上的。当同一个逻辑契约在一张图里被多个节点用到时，怎么对上？——编译器把世界切片下沉成一条**按逻辑契约寻址**（而不是按节点 id 寻址）的 mock 规则，运行时**凡是绑定了该契约的节点，都路由到同一段世界片段**。这就把"契约级的世界"和"节点级的装置"之间的阻抗打通了，也让"同一契约被多个节点复用"变得自然。

剧情与被测版本之间，采用**契约兼容绑定**：剧情绑的是逻辑契约的指纹，只有当契约发生**不兼容**变更时才失效并触发影响分析；无关改动、或仅仅换了个实现切片，都不会误伤。

### 4.5 通信协议：控制走请求头、业务走请求体、大负载按引用解析

发起一次测试/模拟调用时，协议这样切：

```
X-BLOGE-Test-Envelope: base64url(JSON{ purpose, 剧情或世界模型的引用{id,revision,fingerprint}, correlationId })
X-BLOGE-Test-Fidelity / X-BLOGE-Test-Scope: 若干离散的可选控制头
X-BLOGE-Test-Inline:  base64url(有界的内联控制)   —— 仅供临时调试
请求体：业务输入（数据面）
```

**控制数据放进独立的请求头（控制面），业务输入留在请求体（数据面）**。这样控制面可以被网关独立地治理、剥离、签名；生产环境要拦截测试控制，只需在入口看一眼这个头，无需解析请求体。

**大的负载绝不上传输层**：请求头里带的只是剧情/世界模型的**引用**，服务端凭引用去治理资产库里把真实的 fixture 解析出来。这既解决了 HTTP 请求头装不下大响应体（世界里的原始响应可能到 1MB，而请求头通常只有 8–16KB、还会被代理截断）的物理限制，也顺带把真实业务负载挡在了传输层和日志之外。

因为"凭引用解析真实资产"是一条新的、涉及敏感数据的路径，服务端在解析引用**之前**，必须校验"**发起方身份 × 目标租户资产**"的访问权限，没有权限就直接失败；存了真实业务负载的世界模型，要求更高的授权档位。

真实负载本身**分级托管**：默认是脱敏或合成的；只有经过显式授权、且打了分类标签的世界模型，才允许存真实负载（并带保留期与访问策略）。这里有一条硬约束——**执行内核对负载一无所知**：分级、授权、分类、脱敏全部发生在治理与资产层，编译器是唯一的跨层桥梁（它把"已被治理的负载"解析成内核能吃的 fixture 值），"分类""租户"这些概念绝不进入内核的数据类型。

生产隔离做**纵深防御**：入口层对生产流量剥离/拒绝这个控制头；服务端再从"访问入口 + 工作负载身份 + 策略"铸造一个不可伪造的"执行目的"，一旦在生产目的下发现非空的控制计划就直接拒绝。任何一层失守，另一层仍然兜得住。（请求头里的 `correlationId` 只用于关联诊断和去重，测试运行本身是确定且隔离的，不复用外部写操作那套幂等语义。）

### 4.6 表达式函数的返回值注入

内核统一允许对任意函数调用点注入返回值；**是否合法、以及证据算几分，由治理层判定**。分三种情况：

- **环境事实型函数**（身份、特性开关、密钥、时间、随机、ID）：这些其实早已通过确定性执行服务被 fixture 化了，这里只需要在世界模型/剧情层把它们更好地暴露出来。
- **自定义的、包裹了外部查询的函数**（真正的新增能力）：允许注入返回值，但准入前提是——**这个函数必须在它的库定义里显式声明自己是"非纯 / 依赖外部"的**；内核依据函数已有的"是否纯函数""需要哪些执行服务"这些信号来强制。也就是说，只有主动声明了自己不纯的函数才可以被注入返回值并保留契约级证据。
- **对纯函数强行注入返回值**：允许（用于极致隔离某段计算），但这次运行的证据**降为探索级**。

这样既补齐了"函数也能脱离外部依赖模拟"的能力，又不破坏纯函数的可信性，且与现有"拦截非纯函数"的策略完全对齐。

### 4.7 回归影响分析

"改一处，算出受影响的剧情"用两条腿走路：

- **静态依赖图**：每个剧情声明它依赖哪些逻辑契约/资源；当契约发生变化时，对比契约指纹，反查出所有受影响的剧情——**在运行之前**就能算出影响面。
- **运行时消费校验**：复用现有证据里"哪条 fixture 被消费了几次""每个节点走了什么"的数据，反推出剧情**实际**依赖了什么，用来校验并补全静态声明、发现声明漂移。

静态给"先验"，运行时给"纠偏"；而且依赖声明可以从编译产物里自动推导出来，减少人工漏声明。

## 第五部分（也属于解法）· 平台自身的正确性如何验证、如何长期保持

这一部分单独拎出来讲，因为它就是第二部分里那个"最关键的衍生问题"的答案。我们要建的是一个**测试/拟真平台**——它自己必须比它所测的业务更可信。下面从"如何让它天生可测"到"如何证明它对、如何让它一直对"逐层展开。

### 5.1 把可测试性当成架构硬约束，而不是事后补测试

平台的核心组件从一开始就遵守一组**可测试性不变量**：核心逻辑是纯函数；一切副作用源（时钟、IO、随机、身份）一律注入而非直接读系统；不允许隐藏的静态/全局状态；每一步都产出结构化、可指纹的记录；并且用架构级规则（类似 ArchUnit）**禁止核心代码引入任何非确定性 API**（读系统时间、直接取随机、遍历无序集合等）。这样"可测试"是架构的**结果**，而不是事后打的补丁。

### 5.2 信任锚：先彻底验证一个最小可信核，再由内向外逐层验证

"用测试器去测测试器"是有递归风险的——世界片段本身是 BLOGE 图，测它又要跑同一个内核。破解办法是立一个**信任锚**：把最小的一组内核原语（转换/决策表/分支的求值 + 确定性执行服务）用穷尽、属性、乃至形式化的手段**彻底验证**，作为整个体系的可信基准。然后**按依赖顺序由内向外**验证：可信核 → 编译器 → 世界片段求值器 → 各高保真执行模式 → 通信层，每一层只依赖已经被验证过的下一层。

与之配套的是**吃自己狗粮的边界**：可信核本身用最朴素的单元测试来测（它**不能**被它所锚定的东西来测，否则就循环论证了）；而它之上的平台行为（编译、世界片段、各模式、通信）则**尽量用剧情/世界模型来自测**——既真正吃了自己的狗粮，又顺便暴露真实的作者体验。

### 5.3 平台自证：其中编译器是最危险的组件，用三重独立手段交叉验证

- **差分等价**：编译器编译出来的装置包，跑出来的结果，必须与"手写一个等价装置包直接跑"**逐字段一致**；新内核与被它替换的旧路径也必须**结果等价**（这个"等价对拍台"是收敛期删除旧路径的前置门禁）。
- **编译器的正确性 oracle**——因为"和手写等价物对拍"本身有循环性（我要是能手写就不用编译了），所以用三条独立的手段交叉：（1）**结构性质**：每条世界规则恰好映射一条 mock 规则、寻址被保持、不丢不重、来源映射双向一致；（2）**独立参考实现**：另写一个朴素的第二实现来做差分，打破循环；（3）**往返验证**：把编译出的 mock 反投影回世界规则再比对。
- **变形/属性测试**：同样的输入重复跑 N 次，证据指纹必须逐位相同（确定性）；所有 mock 模式必须零副作用；世界片段必须纯。
- **黄金语料**：内核和编译器各维护一组冻结的黄金用例做回归。

### 5.4 资产保真：证明"世界模型≈真实世界"，并在它开始失真时报警

世界片段是"客户世界的地面真值"——它要是错了，所有建立在它之上的剧情都在**对着谎言做验证**。而"形状对"不等于"行为对"，何况真实 API 还会随时间漂移。所以：在受控环境里，周期性地把一批请求同时打给**真实 API** 和世界切片，做契约级的差异比对；差异超过阈值就把该切片标记为"疑似漂移"、报警、并**降低它产出证据的等级**，驱动世界模型更新。此外，从生产/真实运行里**差分派生**出来的期望值，在被晋升为回归标准之前，**必须经过人工复核**——防止把一个线上 bug 当成"期望"固化下来。

### 5.5 充分性：用"元变异"抓出"对错世界也照样通过"的假剧情

标准做法是变异业务图，看剧情能不能抓到"业务规则被改坏"。但对一个世界模型驱动的平台，这还不够——我们还要**变异世界模型/世界片段**，看剧情能不能抓到"世界被改错"。如果把世界改错了、某个剧情却照样通过，说明这个剧情根本没真正依赖并断言世界的行为，它是个**假通过**。两层变异都产出变异得分门禁，并识别等价变异体。再叠加覆盖度聚合（世界规则覆盖、逻辑契约覆盖、fixture 消费命中；没被消费的 fixture 就是覆盖缺口，报警）。

### 5.6 系统级测试与最难测的隔离边界

端到端系统测试床要覆盖整条链路：请求头解析 → 入口剥离 → 目的铸造 → 引用授权 → 引用解析 → 编译 → 执行 → 证据，并且要有**反面用例**（未授权/越权的引用、被损坏的头、超大的引用、生产流量里夹带控制计划）。其中最难测的是跨"应用 / 基础设施"边界的隔离部分，做法是三管齐下：进程内用一个"模拟入口"对剥离逻辑做契约测试 + 在受控环境里对**真实入口配置**做一层薄薄的一致性测试 + 服务端的铸造拒绝作为**独立可测的最终保证**；再用故障注入证明"任意一层失守，整体仍然安全"。

### 5.7 测试金字塔与时间预算

分五层、各有时限预算：内核原语的单元测试（毫秒级、每次提交）；编译器/片段求值器/协议解析的组件测试（秒级、每次提交）；编译+执行+证据+隔离引擎的集成测试（每次 PR）；通信+入口+授权的系统测试与反面用例（合并时）；一致性与受控重放（世界保真、漂移、变异门禁，夜间/受控环境跑）。**前三层是快线，秒级全绿才允许合并；后两层是慢线，异步门禁。**

### 5.8 谁来验证验证器

最后一层递归：验证器自己也可能有 bug（该拒的没拒、黄金语料悄悄过期）。三条纪律兜住它：**反面对照**（准备一批"必须失败"的坏输入——损坏的片段、违约的响应、超阈的漂移；验证器要是放行了，就是验证器自己有 bug）；**变异验证器**（对验证器代码本身做变异测试，确保它真的会拒）；**黄金语料新鲜度**（黄金语料带来源指纹，来源变了而语料没更新就报警，防腐烂）。

### 5.9 失败归因与可观测

为了长期可维护，一次失败必须能被快速定位到层：是世界模型错、编译器错、业务图错、内核错、还是断言错——借来源映射加每层 trace 完成归因。平台还持续输出一组"可信度指标"：各执行模式的分布、世界模型漂移率、变异得分、系统测试覆盖、编译等价通过率。

## 第六部分 · 工程实施计划

四个阶段，每阶段都独立可验证、可交付。每阶段除了"验证被测业务"的出口标准，都额外交付"**验证平台自身**"的测试资产。里程碑验收命令：

```bash
mvn -f resource-gateway-examples/pom.xml clean verify
mvn -f resource-gateway-test-kit/pom.xml clean verify
```

**阶段零 · 收敛内核 + 打通"描述符驱动、只换传输"的地基（不删旧路径）**
把执行模式枚举引入内核；把现有的"临时组装描述符算子 + 传输桩"提升为正式的 `DESCRIPTOR_TRANSPORT` 档位；引入执行选项/执行目的入口；实现结构化控制头的解析（先支持有界内联控制）；落地入口剥离 + 服务端铸造。**这里不删旧的设计期模拟路径**，而是给它加一个适配器让它委托到统一内核，等到新内核在功能和安全上都达到与旧路径**对等**（含节点数/边数上限、超时、逐节点 fixture、混合分类、防 ReDoS/SSRF）之后，再另起一个里程碑移除旧代码。平台自证交付物：新旧路径"等价对拍台"、编译等价台、内核确定性（N 次重放同指纹）台、禁非确定 API 的架构规则。出口：描述符驱动零网络跑通 `httpResource` 的全过程；设计期模拟经适配器走同一内核；生产目的携带控制计划在入口与服务端两处被拒。

**阶段一 · 资产层 + 自举世界 + 编译下沉**
落地逻辑契约（含从描述符投影初稿、切片一致性校验）、世界模型/世界切片（世界片段=纯 BLOGE、纯净校验器、独立单测台）、剧情、编译器（下沉成装置包 + 按逻辑契约寻址 + 委托模式）、契约兼容绑定与指纹差异、引用式解析 + 引用授权 + 分级负载托管、以及三类资产的持久化（复用现有"内存缓存 + 内嵌库 + JSON blob"的成熟模式，不可变 + 递增版本 + 指纹；真实负载入受治理资产库）。平台自证交付物：编译器三重 oracle（结构性质 + 参考实现差分 + 往返）、纯净校验器与片段单测台、来源映射双向一致。出口：无状态世界匹配确定（歧义即失败）；契约兼容只在不兼容时失效；大负载不上传输层；未授权引用直接失败。

**阶段二 · 有状态世界 + 函数返回值注入**
落地内核持有的、每剧情独立的世界状态存储（单写者、确定性排序、可序列化），以及有状态世界片段；落地函数返回值注入的三类与"非纯声明"准入。平台自证交付物：写后读一致 + 跨剧情隔离 + 并发确定性顺序；函数准入正确。出口：证据分级正确（对纯函数强注入降为探索级）。

**阶段三 · 线上沉淀闭环 + 回归影响分析 + 存量迁移**
落地"从生产/真实运行沉淀为世界模型"的通道（显式黄金捕获 + 重放派生、默认脱敏、晋升前人工复核门禁，不做无差别被动录制）；落地回归影响分析（静态依赖图 + 运行时消费校验 + 自动推导声明）；提供把存量测试套件单向"抬升"为剧情+世界模型草稿的工具（加法式、旧通信版本保持兼容）。平台自证交付物：世界保真周期性重放 + 漂移检测、两层变异门禁、端到端系统床（含隔离边界故障注入）、验证器反面对照。出口：沉淀出的世界模型默认脱敏；改契约算出的影响面与运行时消费一致；存量套件可抬升。

**明确推迟**：把这套 fixture/执行控制能力抽象下沉为 BLOGE 框架级扩展点——等到平台的一致性测试、证据字段、生产隔离测试全部稳定、语义定型后，另立专门的架构决策记录再做。

## 第七部分 · 落地之后仍未解决 / 会新暴露的问题，及预计解法

1. **非 HTTP 边界的描述符化**：本方案的"描述符驱动、无需部署实现"目前只覆盖描述符驱动的 HTTP 资源；消息队列、数据库、gRPC 等边界仍然要么需要真实实现、要么需要各自的"描述符"。**预计解法**：等至少两类非 HTTP 边界完成试用后，把"边界描述符解释器"泛化成一个可插拔点，再考虑是否随框架扩展点一起下沉。
2. **有状态世界的并发、重放与快照成本**：并行分支下的状态排序、有状态世界的重放、状态快照的存储开销。**预计解法**：初期限定每状态键单写者 + 确定性排序；后续引入基于血缘的排序与增量快照。
3. **"契约兼容"判定的准确度**：结构兼容不等于语义兼容，可能漏判（漏报了破坏性变更）或误判（无谓地让资产失效）。**预计解法**：先用保守的结构兼容 + 显式的破坏性变更标注，再用真实的差异语料逐步细化。
4. **真实负载资产的数据生命周期**：存了真实负载的世界模型会变成一处敏感数据存储，需要保留策略、被遗忘权、访问审计、跨租户隔离证明。**预计解法**：专设受治理的资产库 + 按分类驱动的策略，全部落在治理/资产层、不进内核。
5. **黄金捕获的脱敏完整性**：从生产抓来的样本即便过了启发式脱敏，仍可能残留敏感信息。**预计解法**：schema 引导的脱敏 + 晋升为真实负载世界模型之前的人工复核门禁。
6. **剧情作者体验与规模化**：世界模型变大之后，剧情的编写与依赖声明的准确性会成为一个产品问题。**预计解法**：画布侧的剧情编写体验 + 从编译产物自动推导依赖声明。
7. **世界片段的表达力上限**：纯原语白名单可能不足以表达某些复杂的外部行为（加密签名校验、复杂分页）。**预计解法**：用一批受控的纯函数库扩展白名单（仍保持纯确定），必要时引入"世界内组合"（一个世界片段引用另一个契约，带环检测）。
8. **自举带来的循环依赖**：世界片段用 BLOGE 原语写，而 BLOGE 引擎又在执行业务图，必须防止两者纠缠。**预计解法**：世界片段在内核的隔离子上下文里求值、不与业务图共享状态、有深度与资源上限、且禁止再触发一次"委托给世界片段"（单层）。
9. **受控重放环境的成本**（新暴露）：契约一致性重放需要一个能打真实 API 的受控环境，长期跑有成本。**预计解法**：低频（夜间）+ 只对采样的契约点重放来控制成本。
10. **可信度门禁把关过严导致的迭代摩擦**（新暴露）：变异门禁、漂移门禁、编译等价门禁如果一刀切，可能拖慢正常迭代。**预计解法**：门禁按证据等级分档——探索级资产宽松、认证级资产严格——让代价与可信度诉求匹配。
